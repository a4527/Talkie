## 미션 평가의 실제 공급자 합성 사례 대조(B-12·B-03 일부)

- 사용자 “다음 진행해” 요청으로 PROGRESS 재개 지점 2의 실제 공급자 비공개 시험 가운데 **평가 판정의 합성 사례 대조**만 진행했다. 음성으로 직접 말해야 하는 토큰 고정 지시·실시간 도구 호출 시험은 하지 않았다.
- 조건: [DEC-056](../DECISIONS.md) 무료 비공개 로컬 시험. 사용자가 `app/.env`에 넣은 Google 키로 호출했다. 키가 무료 프로젝트라는 것은 사용자 진술(`GEMINI_FREE_TIER_CONFIRMED`)이며 청구는 확인하지 않았다. 입력은 [평가 사례](../proposals/FIRST-MISSION-EVALUATION-CASES.md)의 A2 기본 대화와 변형 8개(P-01·P-02·F-01·F-02·U-01·U-02·R-01·R-02)의 고정 합성 대본뿐이다. 개인정보는 없다. 기대값은 2026-11-14에 사용자 검토를 마친 **판정 후보**이며, 승인된 정답표가 아니다.
- 실행 범위와 호출 수는 실행 전에 사용자와 정했다. 1차는 9개 사례 × 3회였다. 이후 사용자가 “각각 한도 확인해서 한도에 맞게 여러 모델로 테스트해봐”라고 해서 모델별 무료 한도(사용자가 공유한 콘솔 표의 RPM/RPD) 안에서 호출 상한을 강제했다.
- 추가한 코드:
  - `app/src/mission/eval-cases.ts`: 고정 대본, 기준 18개의 기대 판정, 문서상 경계 기준, 점수 후보, 비교 함수.
  - `app/tests/mission-eval-cases.test.ts`: 호출 없는 시험. 기대 판정을 앱 합산에 넣으면 문서의 점수 요약(98.5·97·53·48.5·100·100·97)과 같아지는지, 튜터 발화 인용이 거부되는지, 누락 표시가 U-01에만 있는지 확인한다.
  - `npm run mission:eval`(`app/scripts/eval-mission.ts`):
    - 모델 선택, 호출 상한, 최소 호출 간격을 둔다.
    - 모든 시도의 원본 응답과 오류 종류(코드)는 Git 제외 경로 `app/.local/mission-eval/`에 저장한다.
    - 시험 스크립트에서만 모델을 바꿀 수 있도록 `createGeminiExtractionGenerate`에 선택 인자를 더했다. 제품 경로는 계속 `gemini-3.5-flash-lite`를 쓴다.

  - 화제 이탈은 '간결성과 관련성'에서 본다.
  - 주제에는 맞지만 모호한 답은 '필요한 설명·확인·수정'에서 본다.
- 다음 원칙도 더했다.

### 한계와 다음 일

- **과적합 위험:** 프롬프트를 고친 사례로 다시 측정했고, 보지 않은 사례(holdout)는 없다. 정의 보강이 다른 대화에서도 같은 효과를 내는지는 미검증이다. 표본도 사례당 2~3회라 흔들림을 정밀하게 재지 못한다.

- **다음 일:** 80% 경계 근처의 합성 사례와 holdout 사례 추가, 음성 미션의 실제 공급자 시험.

## 과적합 검토: 새 사례(holdout)

- 사용자가 “새사례로 과적합 검토부터 하자”를 골랐다. 평가 지시를 고칠 때 쓰지 않은 [새 사례 6개](../proposals/FIRST-MISSION-HOLDOUT-CASES.md)(H-01~H-06)를 만들고, 판정 후보를 **실행 전에** 문서와 코드(`HOLDOUT_EVAL_CASES`)에 고정했다. 판정 후보의 사용자 검토는 아직 하지 않았다. 호출 없는 시험에서 후보로 계산한 점수가 문서 요약(83.5·73.5·83.5·100·57/57·97)과 같은지 확인했다(시험 5개 통과).
- 실행 조건: `gemini-3.5-flash-lite`, 3차와 같은 평가 지시, 6개 사례 × 3회, 상한 36회. 실제 호출은 20회였다. 실패 응답은 2회(503 1회 포함)였고 미확정은 0회였다.

- **기준 일치율:**
  - 새 사례: 324개 판정 중 303개(93.5%). 불일치 21개 가운데 경계 기준이 10개다.
  - 3차 기존 사례: 432개 중 402개(93.1%).
  - 전체 일치율로는 과적합 증거가 없다.
- **80% 달성 여부:** 18회 모두 후보와 같았다. 다만 H-01은 81.5로 경계와의 차이가 1.5점이고, H-05 2회차는 정확히 80%였다.
- **일반화되지 않은 부분: 기록 누락 처리.**
  - 기존 U-01(설명 발화 누락)에 맞춰 넣은 누락 규칙은, 누락 위치가 다른 H-05(수락 발화 누락)에서 3회 가운데 1회만 해결 항목을 판정 불가로 두었다.
  - 2회는 PRD가 금지한 “직원 확정으로 사용자 수락 추정”을 했다.
  - 이 부분은 조정한 사례의 모양에만 맞춰진 것으로 본다.
- **판정 후보가 의심되는 부분:** H-03의 설명·확인(부분 충족 후보, 경계)은 모델이 3회 모두 충족으로 판정했다. 같은 누락을 목표 항목과 언어 기준에 모두 반영할지는 후보 쪽의 해석일 수 있어 사용자 검토가 필요하다.
- 사전 규칙대로 이 결과로 평가 지시를 고치지 않았다. 고치려면 사용자 검토 뒤 새 holdout이 필요하다.
- **정책 검토 지점:** 현행 정책을 그대로 적용한 결과지만 의도와 맞는지 확인이 필요하다.
  - H-03은 카페인 문제를 해결하지 않고도 80%를 넘는다.
  - H-05는 최종 수락이 누락되면 해결 항목 40점이 제외되고 100%가 될 수 있다.

## 사례 대본의 상대역 규칙 위반 수정

- 사용자가 “수준이 낮아질수록 직원이 알아서 다 해주는 느낌”이라고 지적했다. 정책(PRD 4.2·4.2.1, DEC-076)과 상대역 지시는 수준에 따라 말하기 난이도만 바꾸고, 대신 해결해 주는 정도는 바꾸지 않는다. 그런데 사례 대본 일부에서 직원이 요청 전에 처리를 먼저 꺼냈다. 사용자가 “1,2번 진행해줘”라고 해서 대본 수정(1번)과 직원 행동 점검(2번)을 진행했다.
- 기존 A1 기본 대화:
  - A1-3에서 직원이 먼저 재제조를 제안하던 것을 “원하는 처리 묻기”로 바꾸고, 사용자 요청 A1-4를 넣었다(이후 ID는 하나씩 밀림).
  - 12개 기준 대조표의 A1 열 발화 번호를 맞췄다.
  - A1은 코드 평가 묶음에 없어 실행 결과에 영향이 없다.
- F-02-5에서 직원이 묻지 않은 환불을 먼저 꺼낸 것은 이미 실행한 대본이라 유지했다. 평가 판정에는 영향이 없다고 문서에 표시했다.
- 새 사례:
  - H-01·H-02·H-04는 상대역 규칙 위반으로 표시했다. 평가 판정 시험으로는 유지하고, 상대역 예시로는 쓰지 않는다.
  - 규칙에 맞게 고친 H-07(H-01 수정, 후보 82)과 H-08(H-04 수정, 후보 100)을 실행 전에 고정했다.
- H-07·H-08 실행(`gemini-3.5-flash-lite`, 각 3회, 호출 6회, 미확정 0):
  - H-07: 82(18/18) · 81.5 · 78. 3회차는 정보 순서(경계)를 미충족으로 판정해, 후보는 달성인데 결과가 **80% 미달**로 바뀌었다. 지금까지 달성 여부가 후보와 달라진 첫 사례다.
  - H-08: 3회 모두 100(18/18).

  - 학습자가 구체적인 처리를 요청하면 그 조건만 안내한다.

## 경계 판정 세 가지 결정(DEC-090)

- 사용자가 경계 판정 후보 세 가지에 “b는 추천대로할게”로 동의했다. [DEC-090](../DECISIONS.md#dec-090)으로 기록하고 PRD 4.5.2에 한 문장을 더했다.
  - 처음부터 말하지 않은 목표 조건은 목표 항목에서만 반영한다(설명·확인에서 다시 감점하지 않음).
  - 결정을 바꾸는 것 자체는 앞선 연결의 불일치가 아니다.
  - 어순 오류는 문장 구조에서만 본다.
- 판정 후보 변경:
  - H-03: 83.5 → 85.
  - N-02: 78.5 → 80. 정확히 80%라 달성이 되며, 어순 후보는 유지했다.
  - N-06: 58.5 → 60.
  - 문서와 코드 기대값을 함께 고쳤다.
- 새 후보로 다시 계산한 기존 실행 결과:
  - H 묶음: 기준 일치 306/324(94.4%).
  - N 묶음: 기준 일치 300/306(98.0%). 다만 N-02는 모델이 어순을 단어 조합에서도 감점해 78.5가 나왔고, 새 후보(80, 달성)와 **80% 달성 여부가 3/3 다르다**. 평가 지시의 단어 조합 정의에 “어순 오류는 문장 구조에서 본다”를 넣어 맞추려는 것이며, 그 효과는 새 사례로 확인해야 한다.
- 평가 지시의 기준 정의 세 곳(단어 조합, 설명·확인, 앞선 연결)에 DEC-090을 반영했다. H·N 결과를 본 뒤의 변경이므로 두 묶음은 이 변경의 검증용으로 쓰지 않는다.
- 누락 처리 재확인:
  - 현재 평가 지시에는 이미 “남은 상대역 발화로 누락된 학습자 수행을 추정하지 않는다”가 있다. 이 규칙을 새로 넣자고 한 앞선 설명(A-1)은 잘못이어서 사용자에게 바로잡았다.
  - N-04에서 모델이 처리 요청을 충족으로 본 사유는 “문제를 지적하며 처리 방향을 유도”(1회), “직원의 환불 제안에 동의하여 처리 요청”(2회)이었다. 직원 발화로 추정했다기보다, 문제 설명이나 제안 수락을 처리 요청으로 넓게 인정한 것이다.
  - 저장 쪽은 누락 여부만 불리언으로 기록하고 위치는 남기지 않는다(`hasConversationGaps`). 누락 위치를 표시하려면 저장 계약을 바꿔야 한다.
- 검증: `npm run typecheck` 통과, `npm test` 19개 파일·170개 통과.

## 누락 표시 범위 확인

- A-2(누락 위치 저장) 논의 전에 코드를 확인했다.
  - `hasConversationGaps`는 클라이언트 버퍼가 200턴 또는 직렬화 128 KiB를 넘을 때, 아직 저장 확인되지 않은 가장 오래된 요청 단위가 잘린 경우에만 켜진다(`app/src/learning/buffer.ts`, `app/src/voice/learning.ts`, `app/src/learning/session.ts`). 수십 턴 안에 끝나는 카페 미션에서는 사실상 켜지지 않는다.
  - V-01·H-05처럼 대화 중간의 발화 하나가 빠지는 경우는 현재 코드에서 이 표시로 생기지 않는다.
  - 실제로 생길 수 있는 누락은 빈 전사다. 음성 경로는 텍스트가 비어 확정되지 않은 발화로 턴을 만들지 않으며 누락으로도 표시하지 않는다. 미션 평가는 이런 발화를 알 수 없다.
- 사용자가 “형식 유지, 한계만 기록”을 골랐다. 저장 형식과 평가 지시는 바꾸지 않았고 [학습 저장 설계](../design/LEARNING-PERSISTENCE.md#현재-초기값과-버퍼-유실)에 표시 범위와 빈 전사 한계를 적었다. 누락 시 일수 인정 정책은 B-12 일수 작업에서 다룬다.

## 상대역 수준별 말하기 보정

## 텍스트 경로 남은 점검: 서브 에이전트 4개 동시 실행

- 사용자가 “텍스트 부분 남은 테스트를 전부 서브 에이전트로 동시에 진행”을 요청했다. 네 에이전트는 같은 무료 비공개 프로젝트(`gemini-3.5-flash-lite`, 합성 텍스트, TTS·Live 미사용)를 썼다. 호출 간격은 20초 이상이었다. 앱 코드·지시·문서는 고치지 않고 새 스크립트와 출력(`app/.local/`, 추적 안 함)만 만들었다. 실행 시점의 지시는 위 수준별 보정을 포함한 작업 트리 상태다.
- **한계(공통):** 동시 실행으로 07:10경부터 429가 이어져 일부가 실행되지 못했다. 미실행 항목은 A1 실전 대화, 연습 무진전 대화, 연습 단일 응답, 단일 응답 2회차 일부다. 대부분 상황당 1~2회라 빈도는 방향만 보여 준다.

### 1. 실전 여러 턴(`app/scripts/eval-mission-dialogue-real.ts`, 호출 46/80)

- 앱 모듈(`CascadeAdapter` 가짜 STT/TTS + 실제 `cascadeText`, `VoiceLearningRecords`, `previewMissionEnding`)로 대본 5개를 돌리고 종료 평가까지 연결했다. 서버 종료 사유 계산은 DB가 필요해 판정식을 재현했다.

| 대화 | 기대 | 실제 | 평가 |
| --- | --- | --- | --- |
| 재제조(B1) | 완료/재제조 | 직접 종료/경로 없음 | 100 |
| 환불(C) | 완료/환불 | 직접 종료/경로 없음 | 100 |

- **원인(코드 확인):** 분리형 출력 안내(`app/src/server/voice-cascade.ts:91`)는 `missionReport (routeEvents: [{kind, routeId}], progress)`만 적고 허용값을 강제하지 않는다. 모델이 학습자 수락을 `progress: "user_accepted"`로 넣었고, 파서(`app/src/mission/realtime.ts:63`)는 `progress`가 허용값이 아니면 보고 전체를 버린다. 그래서 같은 보고의 `staff_confirmed`까지 사라졌다. 경로 변경 대화는 `user_accepted`만 빠졌다. 검증기는 수락 없는 확정을 완료로 보지 않았고, 이는 설계대로다.
- **평가와 기록 불일치:** 입력은 `user_ended`·최종 경로 없음인데 평가는 대화 내용으로 최종 합의를 충족시켰다. 결과 화면이 “미완료”이면서 목표가 만점일 수 있다.
