## DEC-062 연결 시간 이용권·주간 과금 대조 승인

- 사용자가 [시간만 집계·시간 이용권과 최소 계측·토큰 집행 비교](../proposals/API-USAGE-BUDGET.md#새-방향-검토-시간활동량과-주간-과금-대조)를 확인한 뒤 추천한 B안에 “동의해. 관련 문서 하나도 빠짐없이 변경해줘”라고 명시적으로 동의했다. [ADR-062](../adr/062-TIME-BASED-VOICE-ALLOWANCE-AND-WEEKLY-COST-REVIEW.md)로 계정/기간별 공급자 연결 허용 시간·동시/연결당 제한, 별도 노트 호출 제한, 경로별 주간 실제 과금 대조를 채택했다. DEC-060/061의 토큰 원장·예약/정산·환산식은 대체했고 90일 토큰 원장 보존안은 채택하지 않았다.

- 문서·구현 대조: 현행 180초 비공개 토큰과 프로세스 메모리 요청 제한은 기간 시간 이용권이 아니다. 분리형 Gemini 사용량 추출 함수는 라우트에 연결되지 않고 시간 차감에도 쓰이지 않는다. 주간 과금 조회·연결 시간 상태·노트 호출 제한·공급자 지출 경계는 미구현이고 B-10 TODO를 유지했다. 시간/기간/환급·보존·노트/지출 수치, 교정/재시도 마무리 경험, 유료 실측과 최종 공급자 경로는 후속이다. 새 공급자 호출·추가 E2E는 수행하지 않았다.
- 최종 대조: PRD F-02/F-09와 6·9.2절, DEC-059~062의 상태/대체 관계, B-06/B-09/B-10/V-05의 수용 기준, PROGRESS의 B-10 TODO와 CHANGELOG의 당일 대체 이력을 확인했다. 변경 Markdown의 상대 링크 경로 검사와 `git diff --check`가 통과했다. 수치·보존·공개 집행은 아직 미정이므로 결정/완료로 표시하지 않았다.

## 실제 공급자 사용량 보고 시험

- 사용자가 실제 호출을 요청했다. 로컬 `.env`의 Google/Soniox 키 존재만 확인하고 값은 출력하지 않았다. 2026-10-30 07:04~07:06 UTC, Node 24.22에서 합성 텍스트와 무음 PCM을 사용해 Gemini 텍스트·TTS·Live 각 1회, Soniox STT 정상 종료·중단 각 1회를 호출했다. 공급자 응답의 내용·음성·키·임시 토큰·원시 요청/응답은 출력/저장하지 않고 상태와 사용량 숫자만 확인했다. 기존 추가 E2E 보류와 별개로 이 제한된 공급자 계측 시험만 수행했다.
- Gemini `generateContent`: `gemini-3.5-flash-lite` 텍스트는 HTTP 200, 입력 8·출력 2·합계 10토큰이었다. `gemini-3.8-flash-lite-tts`는 HTTP 200, 입력 텍스트 2·출력 음성 26·합계 28토큰과 약 49,920바이트의 생성 음성을 반환했다. 둘 다 서버에서 사용량 메타데이터를 받을 수 있음을 확인했지만 현재 앱은 이를 읽지 않는다. 실제 청구액은 대조하지 않았다.
- Gemini Live: 임시 토큰 발급 HTTP 200, 직접 WebSocket 연결·설정·짧은 합성 텍스트 요청·완료·정상 닫힘(1000)을 확인했다. 공급자 메시지 1개에서 `usageMetadata` 입력 495·총 520·추론 24토큰과 입력 종류별 텍스트 307·음성 168토큰을 받았다. 이 시험에서는 `candidatesTokenCount`가 없었으므로 나머지 출력 과금량을 추정하지 않는다. 메타데이터는 클라이언트 연결에서 관찰했으며 서버 독립 확인·사후 청구 대조는 하지 않았다.
- Soniox: 서버가 `client_reference_id`를 묶은 단일 사용 임시 키를 각각 발급(HTTP 201)했다. 정상 연결은 무음 PCM 약 1초를 보내고 빈 텍스트 프레임으로 완료했다. 완료 사용 기록은 입력 음성 1,080ms·9토큰·$0.000054였다. 중단 연결은 오디오 전송 뒤 약 300ms에 WebSocket을 닫았고 완료 메시지는 없었으나, 사용 기록에 입력 음성 276ms·2토큰·$0.000004가 나타났다. 사용 기록 조회 HTTP 200에서 해당 무작위 식별자로 두 요청을 구분했다.
- 두 Soniox 기록 모두 연결 직후 첫 조회(정상 종료 약 2초 후, 중단 약 2초 후)에서는 없었고 이후 조회(각각 종료 약 15초·23초 후)에서 보였다. 이 결과는 사후 정산 후보를 확인하지만 보고 지연의 최대치나 연결 중 집행을 증명하지 않는다. 모든 숫자는 단일 짧은 합성 시험의 관찰값이며 실제 사용자 음성·다른 길이·재연결·동시 탭·프로세스 재시작·청구서 대조·예약 초과 오차는 미검증이다. Google 무료 등급 적용과 Soniox 기록액을 전체 세션 비용으로 합산하지 않는다.
- 문서 대조: DEC-060/061과 PRD의 사용량 계약, 음성 설계의 현재 미구현 상태, B-10 TODO를 유지했다. 검토안과 PROGRESS에는 관찰 요약만 연결하고 한도 수치·최종 경로·운영 적합성을 확정하지 않았다.

## Orca WSL Git 확인과 분리형 worktree 생성

- 사용자의 작업 공간 분리 요청과 후속 WSL Git 지원 확인 요청을 처리했다. Orca의 Talkie 등록은 `kind: folder`였고 최초 voice-cascade 생성은 원본 폴더를 공유하는 가상 작업 공간이었다. 실제 Git worktree 생성으로 잘못 보고하지 않고 Git 목록과 대조했다.
- Windows Git의 `dubious ownership` 오류를 Orca 문제의 원인으로 단정한 설명을 정정했다. 설치된 Orca 1.4.243의 `app.asar.unpacked/out/main/chunks/runner-C8F4JwPf.js`를 읽어 WSL 경로를 배포판/Linux 경로로 해석하고 `wsl.exe`로 Git을 실행하는 분기를 확인했다(일반 파일 읽기의 정적 관찰). `host list`에 Windows만 나오는 것은 이 WSL 실행 기능의 부재를 의미하지 않는다. REA 전체 패키지 분석은 완료 결과를 얻지 못해 판정 근거에서 제외했다.
- `project setup-update --kind git` 지원을 확인했다. 전환을 막는 추가 폴더 작업 공간에 빈 셸만 있음을 확인한 뒤, 앞서 만든 중복 voice-cascade만 제거했다. 원본 경로/파일을 유지하고 Git 등록으로 전환했다. 전환 후 Orca가 main/origin/main·56b936b를 정상 조회했다. Windows Git의 전역 신뢰 설정은 변경하지 않았다.
- Orca의 worktree 생성 경로를 WSL의 `/home/taemin/Talkie-worktrees`로 지정하고 main(56b936b)에서 실제 `/home/taemin/Talkie-worktrees/Talkie/voice-cascade`와 `a4527/voice-cascade` 브랜치를 만들었다. 원본의 자식 관계로 등록했다. 별도 에이전트·설정 훅·앱/DB·공급자 호출은 실행하지 않았다. 기존 미커밋 검토 문서는 원본에 보존하며 새 worktree에 자동 복사하지 않았다.
- 제품 정책/설계·TASK 상태 변경은 없으며 기록은 이 worklog에 한정한다. 새 worktree는 구현 전 준비 상태다. Git worktree 목록·새 브랜치/기준 커밋·깨끗한 새 작업 공간·원본 변경 보존과 git diff --check를 확인한다.
