## 첫 카페 미션 최소 계약 검토안 작성

- 사용자 “이어서 진행하자” 요청으로 PROGRESS 재개 지점 2를 진행했다. [미션 설계](../design/MISSIONS.md)·[API](../design/API.md)·[DB](../design/DATABASE.md)·PRD 4~6·8절과 현재 코드(`app/src/server/learning.ts`·`records-schema.ts`·`transcripts-schema.ts`·`voice/learning.ts`·`note-extraction.ts`)를 대조했다.
- 코드 확인 사항: 서버 `readConfirmed`가 확정 순번까지의 저장을 턴 ID로 병합하므로 클라이언트 128 KiB 창과 별개로 전체 대화 재구성이 가능하다. 실시간 구조화 도구는 교정/재시도용 하나이며 미션 진행 도구는 없다. 노트 추출 상한은 6청크×30,000자다.

- 문서 대조: 제안서 색인과 PROGRESS 재개 지점 2를 갱신했다. TASK 상태·DEC·CHANGELOG는 바꾸지 않았다(사용자 동작 변경 없음).

## 최소 연결 계약 결정(DEC-086~089)

- 검토안의 Q1~Q4를 질문했다. 사용자 답: Q1 “코드 레지스트리”(추천), Q2 “평가가 끝나면 학습 노트 작성 혹은 학습 노트 작성 후 평가 이런식으로”(분리 순차, 순서는 추천대로 평가→노트로 기록), Q3 “점수 집계만 장기 보관”(추천 아님), Q4 “평가 재시도”(추천).
- Q3은 사용자 데이터 보관 약속의 변경이므로 ADR-088로 남겼다. 해석: 기준별 판정·사유는 DEC-017/018 기간(무료 30일·유료 무기한), 원문 없는 집계는 요금제와 관계없이 탈퇴 전까지 보관한다. 일수 날짜/소급은 여전히 B-12 미정이다. 나머지는 짧은 결정 DEC-086·087·089로 기록했다.
- 반영 순서: PRD 4.5(근거 불일치 재시도·기한 내 미확정 시 점수/일수 없음)·8절(호출 구성·원문 삭제 조건·집계 보관)·11절 색인 → DECISIONS/ADR-088 → [미션 설계 최소 연결 계약](../design/MISSIONS.md#최소-연결-계약)(정의·시작 API·세션 고정·진행 상태·실시간 도구·종료 처리·결과 저장) → DB/API/학습 노트 설계의 연결 문장 → TASKS B-06·B-12 수용 기준 → 검토안 결과·색인·PROGRESS·CHANGELOG.
- 확인 사항: 기존 만료 작업은 `learning_session_notes`만 지우고 `learning_sessions` 행은 남기므로 집계를 학습 세션에 FK로 연결해도 30일 만료로 사라지지 않는다(`app/src/server/maintenance.ts`). 테이블·도구 이름은 가칭이며 코드·DB·TASK 상태는 바꾸지 않았다.

## DEC-087 호출 방식 변경: 동시 호출

- 사용자가 순차 호출에서 첫 호출 성공 시에만 두 번째를 호출하고 실패한 쪽만 재시도하는 방식을 설명하며 순서 추천을 요청했다. 둘 다 성공하면 비용은 같고, 차이는 한쪽이 끝내 실패할 때뿐이라고 비교했다. 노트는 이미 구현됐고 부분 저장을 허용하며 11월 2일 합성 시험 8회에서 구간 실패가 0건이었다. 평가는 기준 누락·근거 불일치 시 전체 재시도라 실패 가능성이 더 클 것으로 추정했다(실측 없음). 이 비교로 노트→평가를 추천했다.
- 사용자가 “그냥 동시에 호출하는게 좋겠다. 그것도 실패한것만 호출하는거잖아. 이게 기존내용이지?”라고 답했다. 기존 기록은 평가→노트 순차이고 동시 호출은 새 내용이라고 정정한 뒤, 사용자 선택에 따라 DEC-087을 동시 요청·실패한 쪽만 재시도로 고쳤다. 원문은 둘 다 확정된 뒤 삭제한다. 절충은 사용자 지적(“하나가 실패한다고 다른 하나를 다시 시도하는게 아니잖아”)에 따라 정정했다. 한쪽 실패로 다른 쪽을 재호출하지 않아 둘 다 성공하면 비용이 같다. 순차보다 비싼 경우는 순차였다면 뒤 호출을 생략했을 때뿐이다. 이어 사용자가 실패 확률이 같으면 각 2회 실패 후 성공해도 두 방식의 호출 수가 같다고 지적해, 기한 안에 결국 성공하면 비용이 같고 차이는 기한 내 한 번도 성공하지 못하는 경우뿐이라고 DEC-087 문장을 다시 정리했다.
- 반영: DECISIONS DEC-087, PRD 8절, 미션 설계(호출 구성·종료 처리, 동시 확정 시 원문 삭제 경쟁), 학습 노트 설계, TASKS B-06, CHANGELOG, 검토안 결과. 코드는 바꾸지 않았다.

## 실시간 미션 도구와 클라이언트 창 경계(B-03 일부)

- 사용자 “다음 진행하자” 요청으로 PROGRESS 재개 지점 2의 실시간 미션 도구를 구현했다. 기준은 [최소 연결 계약](../design/MISSIONS.md#최소-연결-계약)의 실시간 도구·진행 상태와 PRD 4.2.1·4.2.2·4.3이다.
- `app/src/mission/realtime.ts`: 도구 선언 `report_mission_state`(경로 사건 4종·실전 `progress`), 엄격한 보고 파서, 경로 완료 판정 `findCompletedRoute`(같은 경로의 제안 < 수락 < 직원 확정, 수락과 확정 사이 다른 경로 변경 없음), `MissionTracker`(재생 완료된 상대역 응답에만 보고 반영, 무진전 연속·초기화, 완료 우선, 128 KiB 창 안 근거만 스냅샷에 포함).
- `VoiceLearningRecords`에 미션 설정을 받아 `mission-report` 사건을 확정 시점에 반영하고, 실전에서는 교정 결과를 무시한다. Gemini Live 어댑터는 미션 도구 호출을 같은 사건으로 바꾸고, 분리형은 서버 텍스트 호출의 `missionReport`를 같은 검증기로 넘긴다.
- `app/src/mission/prompt.ts`(서버 전용): 상대역이 처음 아는 사실/들어야 아는 사실/규칙·경로 조건·모드·상대역 말하기 수준·도구 사용 지시. 토큰 라우트가 세션의 고정 정의로 지시를 만들어 토큰 제약에 넣고 브라우저에는 `missionMode`만 준다. 브라우저 설정은 지시 없이 도구만 보낸다. 시작 응답의 공개 미션에 `routeIds`를 더했다(경로 ID는 계약상 비공개 정보 아님).
- 함께 고친 점: 분리형 브라우저 공급자가 요청마다 저장 스냅샷 전체를 함께 보내던 것을 세션 ID·연결 토큰만 보내도록 줄였다(서버는 원래 쓰지 않음).
- 해석해 정한 구현 경계(계약 범위 안): 수락·경로 변경 근거는 응답 대상 사용자 턴, 제안·확정 근거는 응답 턴. 응답이 중단된 뒤 이어진 사용자 발화는 재생된 질문에 대한 응답 기회가 아니므로 세지 않고 연속을 끊는다. 보고 누락도 연속을 끊는다(사용자에게 불리하게 추정하지 않음).
- 검증: `npm run typecheck` 통과, `npm test` 16개 파일·147개 통과(새 `tests/mission-realtime.test.ts` 15개: 파서, 완료 순서/경로 변경, 미재생 보고 제외, 정의 밖 경로 제외, 서버 진행 상태 검증 통과, 실전 무진전 3회 실패·초기화 조건, 응답 기회 조건, 완료 우선·연습 무시, 실전 교정 무시, 창 밖 사건의 완료 유지·재개, 브라우저 설정의 지시 제외·모드별 도구, Gemini 보고 사건, 분리형 서버 지시·보고, 토큰 라우트). 시험 전용 DB(`talkie_test_rt_*`, 합성 데이터, 실행 후 삭제)에서 `tests/server.test.ts` 29개 중 28개 통과·1개 skip(실제 백업/복원). 미션 세션의 음성 맥락이 고정 정의를 읽고 자유 대화는 읽지 않음을 추가 확인했다.
- 한계: 실제 Gemini/분리형 호출은 하지 않았다. 토큰 제약의 지시가 지시 없는 브라우저 설정보다 우선하는지(공식 문서의 서버 측 지시 유지 설명만 확인), 도구 호출 빈도·판단 품질, 무진전 사례표 대조는 미확인이다. 검증기가 낸 완료/실패 결과로 대화를 끝내고 종료 사유를 기록하는 연결과 무진전 실패의 마무리 대사는 아직 없고, 미션 선택 화면이 없어 UI에서 미션을 시작할 수 없다.
- 문서 대조: MISSIONS 최소 연결 계약 상태·실시간 도구 구현 메모, API 시작 응답·토큰/분리형 응답, VOICE 프롬프트 절, PROGRESS 재개 지점 2·B-03 행을 갱신했다. 사용자 화면 변화가 없어 CHANGELOG·TASK 상태·DEC는 바꾸지 않았다.

## 미션 종료 연결과 종료 사유 기록(B-03 일부)

- 사용자 “하고 다음 진행해” 요청으로 앞 작업을 커밋(`7c7af11`)한 뒤 [최소 연결 계약](../design/MISSIONS.md#최소-연결-계약)의 종료 연결을 구현했다. 평가 호출·결과 저장은 다음 단계로 남겼다.
- 서버 `recordMissionEnd`: `end` 직후가 아니라 최종 저장이 끝난 노트 단계(`completeLearningNote` 첫 트랜잭션, 정리 작업의 노트 처리)와 24시간 자동 종료 때 미션 행을 잠그고 한 번만 기록한다. 확정 저장을 다시 읽어 브라우저와 같은 `findCompletedRoute`로 경로 완료를 확인하고, 실전은 최신 저장의 무진전 연속이 임계값(시험값 3) 이상이면 `no_progress_failed`, 그 외는 `user_ended`/`resume_expired`다. 클라이언트가 보낸 사유는 받지 않는다.
  - 이유: 현재 클라이언트는 `end`를 먼저 보내고 마지막 저장을 이어 보내므로 `end` 시점에는 최종 진행 상태가 서버에 없을 수 있다.
- 브라우저: 검증기 결과가 확정되면 그 응답 재생 뒤 자동으로 `end`한다. 결과가 이미 확정된 미션을 재개하면 연결하지 않고 종료한다.
- 실전 실패 마무리 대사: `MissionTracker.previewEnding`이 응답 전에 같은 규칙으로 실패 여부를 미리 판단한다. Gemini는 도구 응답에 `missionEnding`과 마무리 지시를 넣고, 분리형은 `closing: "no_progress"` 텍스트 호출을 한 번 더 해 그 문장을 말한다(서버는 실전 미션에서만 허용). 실패 확정은 여전히 마무리 대사 재생 뒤다. 마무리 대사가 끊기면 실패가 확정되지 않고 연속도 끊겨 대화가 이어진다.
- 검증: `npm run typecheck` 통과, `npm test` 16개 파일·152개 통과(미리 판단 조건·완료 우선, Gemini 도구 응답, 분리형 두 번째 호출, 서버 마무리 지시·연습 거부 추가). 시험 전용 DB(`talkie_test_rt_*`, 합성, 실행 후 삭제)에서 `tests/server.test.ts` 30개 중 29개 통과·1개 skip. 새 DB 시험: 완료→`goal_completed`·`remake`, 한 번만 기록, 순서가 틀린 사건은 `user_ended`, 실전 무진전 3→`no_progress_failed`, 2→`user_ended`, 연습은 무진전으로 실패하지 않음, 저장 없음, 24시간 자동 종료→`resume_expired`. 이 시험은 추출 실패 재시도 대기 때문에 약 15초 걸린다.
- 한계: 실제 공급자에서 도구 응답 지시를 따라 마무리하는지, 분리형 추가 호출의 지연은 확인하지 않았다. 완료되지 않은 세션의 최종 경로는 비운다(평가 입력에 마지막 선택 경로가 필요한지는 평가 호출 구현 때 확인). 미션 선택 화면이 없어 UI 시연은 불가하다.
- 문서 대조: MISSIONS 최소 연결 계약(상태·세션 고정 기록 시점·종료 연결), API 분리형 `closing`·종료 사유 기록, PROGRESS를 갱신했다. 화면에서 미션을 시작할 수 없어 CHANGELOG·TASK 상태·DEC는 바꾸지 않았다.
