## 실제 공급자 합성 음성

- Gemini Live B1 연습으로 합성 발화 4개를 넣는 세션을 3회 실행했다. 무료 비공개 프로젝트에 합성 음성만 보냈다. eSpeak NG와 라이브러리는 임시 디렉터리에 풀었고, 시험에서만 자동 발화 감지를 끄고 시작·종료를 명시했다. 브라우저 초기 설정에는 미션 지시 없이 도구만 넣었고 재생 완료는 모의로 전달했다. Live 대본은 주문 불만과 환불 요청·동의에 집중했다.
- 1·2회는 같은 주문 불만에서 시작했다. 세션마다 전사·음성 응답 4개와 학습 도구 결과 3개를 받았다. 두 회 모두 교정 제안이 없었고, 환불 조건 제안 사건이 누락돼 수락·확정 기록만으로 앱이 완료를 확정하지 않았다.
- 문장 구조 오류가 더 큰 합성 발화를 사용한 3회차에서 미션 보고 3개, 환불 제안 → 수락 → 확정, 앱의 `goal_completed`를 확인했다. 모델이 한 번 교정 문장을 말하고 다시 말하기를 요청했지만 교정 도구의 `original`이 입력 전사와 달라 앱이 저장하지 않았다. 첫 두 전사도 합성 대본과 달랐다. 음성의 재시도 판정은 검증되지 않았다.
- 분리형 Gemini TTS는 합성 교정 문장 1건을 호출해 24 kHz PCM 259,200바이트를 받았다. 하루 무료 한도 10회 중 이 시험은 1회 호출했다. 분리형 STT부터 재생·종료까지 이어지는 실제 음성 대화와 실제 장치 청취는 이번 시험에 포함하지 않았다.

- 별도 합성 회귀 시험에서 도구 단계의 중간 완료 신호 뒤에 입력 전사 조각을 보내자 앱이 이미 사용자 턴을 확정해 뒷부분을 버렸다. Live 어댑터는 이 지점에서 입력을 열어 두고 실제 응답이 완료되면 전체 입력을 먼저 확정한다. 교정 원문 일치와 재생 근거 검증은 그대로 적용한다. [음성 설계](../design/VOICE.md#생성재생전사-범위)
- Live 미션 도구에 처음 조건을 설명하는 응답에서는 제안을 보고하고 동의를 물은 뒤 다음 발화를 기다리도록 명시했다. 제안과 직원 확정이 같은 턴에 있고 나중에 수락만 오는 순서는 기존 검증기가 완료로 인정하지 않는다는 회귀 사례를 추가했다. [미션 설계](../design/MISSIONS.md#최소-연결-계약)

## Live 교정 뒤 성공·실패 재시도 시험

- 무료 비공개 Live B1 연습에서 합성 주문 불만을 보냈다. 모델이 다시 말하기를 요청하면 성공 대본은 도구가 제공한 교정 표현을 eSpeak NG로 합성하고 실패 대본은 초기 발화의 같은 음성을 반복했다. 이어 환불을 요청하고 동의했다. 합성 시험에서만 발화 경계를 명시했고 어댑터 이벤트와 앱 스냅샷을 대조했다. 재생 완료는 모의 신호이며 실제 마이크·DB는 연결하지 않았다.
- 현행 설정의 성공 목표 표본은 응답 5개에서 교정 제안이 없어 다시 말하기 단계에 진입하지 않았다. 같은 오류의 음성을 반복한 실패 목표 표본에서는 교정 제안과 `retryOutcome: failure`, 짧은 실패 피드백 뒤 역할극 복귀가 모두 나왔다. 최초 교정 도구가 전체 입력 전사에서 인사말과 주문 조건을 빠뜨렸고, 재시도 도구 원문에서도 전사의 `ordered`와 도구의 `order`가 달랐다. 교정과 시도는 스냅샷에 남지 않았다. 두 표본 모두 환불 목표를 완료했다. 근거는 `app/.local/mission-live-smoke/retry-success.jsonl`·`retry-failure.jsonl`이다.
- 공개 API는 입력 전사를 서버가 클라이언트에 보내는 출력 필드로 보내며 다른 서버 메시지와의 순서를 보장하지 않는다. 공개 계약에서 모델이 도구 호출 시점에 그 전사를 그대로 참조할 수 있다는 보장은 확인하지 못했다. [Gemini Live WebSockets API](https://ai.google.dev/api/live#bidigeneratecontentservercontent)
- 합성 전용으로 현재 입력 전사를 반환하는 조회 도구를 추가한 대조에서는 5개 응답 중 3회 모델이 조회해 앱 측 전사를 받았다. 이후 교정 기록 도구 호출은 없었다. 전사를 모델에 전달할 수 있다는 점은 확인했지만 교정·재시도에는 연결되지 않았다. 조회 도구는 로컬 시험에서만 사용했다. 근거는 `app/.local/mission-live-smoke/retry-read-success.jsonl`이다.
- 대체 대본에서는 “for to fix it”이 전사에 남았다. 성공 목표 표본에서 모델은 “to fix it”을 교정하고, 그 표현을 다시 들은 뒤 `success`를 보고하고 역할극으로 돌아갔다. 재시도 근거는 일치했지만 최초 교정 도구 원문에서 인사말 뒤 쉼표가 빠져 교정과 시도 모두 확정되지 않았다. 실패 목표 표본은 교정의 원문·출력 근거와 재시도 원문이 모두 일치했다. 모의 재생 뒤 앱 스냅샷에 교정 1건과 실패 시도 1건이 남았고, 학습 상태는 `retry`에서 `conversation`으로 돌아갔다. 두 표본 모두 이후 환불을 완료했다. 근거는 `app/.local/mission-live-smoke/retry-alternate-success.jsonl`·`retry-alternate-failure.jsonl`이다.
- 인사말을 뺀 짧은 대본에서는 두 표본에서 음성의 `drink`가 입력 전사에 `link`로 기록됐다. 모델은 교정과 각각 성공·실패 피드백을 제공했지만 교정 도구 원문은 전사와 달라 두 표본 모두 스냅샷에 교정이 남지 않았다. 근거는 `app/.local/mission-live-smoke/retry-short-success.jsonl`·`retry-short-failure.jsonl`이다.
- 원문이 다를 때만 앱 전사를 돌려주고 다시 보고하게 하는 합성 전용 대조는 같은 대체 대본으로 1회 실행했다. 교정·재시도 도구 원문이 처음부터 정확히 일치해 재보고 분기는 실행되지 않았다. 모의 재생 뒤 교정 1건과 성공 시도 1건이 같은 스냅샷에 남았고 `conversation`으로 돌아갔다. 모델은 역할극 질문으로 복귀했고 성공 피드백은 말하지 않았다. 성공 기록 경로는 확인했고 불일치 복구 효과는 미검증이다. 근거는 `app/.local/mission-live-smoke/retry-reconcile-success.jsonl`이다.
- 현행 설정으로 대체 성공 대본을 한 번 더 실행했다. 모델은 성공을 보고하고 역할극으로 돌아갔지만, 교정과 재시도 양쪽의 원문이 맞지 않아 저장되지 않았다. 재시도 전사는 마지막 단어 `it`을 빠뜨렸다. 근거는 `app/.local/mission-live-smoke/retry-alternate-success-repeat.jsonl`이다.
- [PRD 4.3](../PRD.md#43-교정과-다시-말하기), [DEC-092](../DECISIONS.md#dec-092), [TASKS B-04·B-09](../TASKS.md#첫-학습-흐름과-기능-구현)의 완료 기준을 대조했다. 시험 전 처리는 로컬 스크립트에 한정했다. 현행 검증 규칙과 작업 상태를 유지한다. 음성·미션 관련 단위 시험 51개와 `git diff --check`를 통과했다.

## Live 전사 불일치 후 재보고 검증

- 무료 비공개 B1 연습에서 합성 음성으로 교정과 성공 재시도만 점검했다. 원문이 다르면 현재 앱 전사를 도구 응답으로 돌려주고, 모델에 그 전사를 근거로 한 번 다시 판단해 보고하도록 지시했다. 로컬 시험 스크립트에서만 적용했고, 발화 경계는 수동으로 알렸다. 재생 완료는 모의 신호였으며 실제 장치·DB 저장·미션 종료는 시험 범위에서 제외했다.
- 첫 실행에서 구두점과 대소문자가 달라 불일치 응답을 보냈다. 모델은 같은 턴에서 다시 보고하지 않고 교정을 말했으며, 다음 턴에서 재시도를 성공으로 보고했다. 앱에는 교정과 성공 시도가 모두 남지 않았다.
- 짧은 대본에서는 합성 발화의 `drink`가 앱 전사에 `link`로 들어갔다. 모델은 불일치 응답 뒤 앱 전사와 일치하는 원문으로 도구를 다시 호출했고, 교정을 제안하지 않은 채 역할극으로 돌아갔다. 앱에는 교정이 남지 않았다.
- 첫 대본을 반복한 세 번째 실행에서는 모델이 앱 전사와 일치하도록 다시 보고했고, 모의 재생 뒤 교정 1건이 남았다. 다음 턴에서는 성공 피드백을 말하고 역할극으로 돌아갔으나 재시도 도구를 호출하지 않아 시도가 기록되지 않았고 앱 상태는 `retry`에 머물렀다.
- 총 3회 모두 교정 도구의 원문 불일치 응답까지 도달했다. 2회는 같은 턴의 재보고에서 원문이 일치했고, 그중 1회는 교정을 기록했다. 교정과 성공 시도가 함께 남은 실행은 0회였다. 로컬 근거는 `app/.local/mission-live-smoke/retry-reconcile-followup-{1,2,3}.jsonl`이다.
- 첫 실행의 두 턴을 로컬 기록기에 재생했다. 관측 그대로는 교정·시도 0건이었다. 도구 인용문만 앱 전사와 정확히 일치하도록 한 대조에서는 재생 확인 뒤 교정 1건·성공 시도 1건이 남았고, 재생 신호를 빼면 둘 다 남지 않았다.
- 앞 절의 현행 설정 로그에서 교정 또는 시도 판정에 연결된 원문 불일치 8건을 확인했다. 3건은 대소문자·구두점 차이였고 5건은 단어·어형 차이나 누락이 있었다. 표기 차이만 허용하는 방식의 효과는 이 표본에서 최대 3건으로 제한되며, 의미 차이까지 허용할 근거는 없다.
- [PRD 4.3](../PRD.md#43-교정과-다시-말하기)·[공급자 데이터 조건](../PRD.md#provider-data-policy), [DEC-092](../DECISIONS.md#dec-092), [음성 설계](../design/VOICE.md#생성재생전사-범위), [TASKS B-04·B-09](../TASKS.md#첫-학습-흐름과-기능-구현)를 대조했다. `npm test` 20개 파일 179개, `npm run typecheck`, `git diff --check`를 통과했다.

## Live 재시도 결과를 발화 전에 보고

- 기존 Live 미션 연습의 `record_learning_result` 설명에 다시 말하기를 요청한 뒤 다음 응답의 순서를 명시했다. 먼저 도구를 호출하고, 실제 시도는 결과와 `conversation`을 함께 보내며, 건너뛰기는 결과 없이 `conversation`을 보고한다. [음성 설계](../design/VOICE.md#생성재생전사-범위)
- 카페 B1 무료 비공개 시험에서 동일한 합성 불만으로 시작했다. 성공은 모델이 제안한 교정 표현을 합성해 보냈고, 실패는 초기 발화를 그대로 반복했다. 건너뛰기는 건너뛰겠다는 말과 환불 요청을 함께 보냈다. 기존 설명과 보강 설명에서 도구·음성 메시지 순서와 모의 재생 뒤 스냅샷을 비교했다. 전사 불일치 재보고 처리는 사용하지 않았고, 발화 경계는 합성 시험에서만 명시했다.
- 기존 설명의 성공 대본에서는 모델이 “Great!”라고 말했지만 결과 도구를 생략했다. 실패 대본에서는 음성 전에 실패를 보고했지만 원문이 일치하지 않아 기록되지 않았다. 두 대본 모두 최초 교정의 원문도 일치하지 않았다.
- 1차 보강 설명의 성공·실패 대본에서는 교정이 저장된 뒤 음성 전에 올바른 결과로 도구를 호출했다. 모의 재생 뒤 각 시도가 저장되고 상태가 `conversation`으로 돌아갔다. 실패 응답은 짧은 피드백을 말했고, 성공 응답은 바로 역할극으로 돌아갔다. 성공 피드백 순서를 도구 설명에 추가한 별도 성공 시험 1회에서는 음성 전 성공 보고, “Great!”와 역할극 복귀, 스냅샷의 성공 기록을 모두 확인했다.
- 건너뛰기 대본이 재시도 요청 뒤 실행된 기존 설명 1회와 1차 보강 설명 2회에서는 미션 상태 도구가 환불 제안을 보고했지만 학습 기록 도구는 호출되지 않았다. 최초 교정이 저장된 기존·1차 보강 각 1회에서는 앱이 `retry`에 머물렀다. 미션 상태 도구에도 학습 기록을 먼저 보고하도록 적은 대조 1회에서는 두 도구가 음성 전에 호출됐고, 환불 조건을 물은 뒤 앱이 시도 기록 없이 `conversation`으로 돌아갔다.
- 두 보강을 합친 뒤 같은 대본에서 성공 1회는 음성 피드백과 시도 기록이 일치했다. 실패 2회는 최초 교정 원문이 모두 달랐고, 이 중 한 번은 실패 보고도 생략됐다. 건너뛰기 2회는 모두 학습 기록과 미션 상태를 음성 전에 보고했지만 최초 교정 원문이 달라 앱의 대기 상태에서 복귀하는 경우는 재현하지 못했다.
- 인사말과 주문 불만을 뺀 짧은 합성 대본 2회에서는 전사에 `for the fix it`이 들어갔고 모델이 교정을 제안하지 않아 재시도 검증에 들어가지 않았다. 전체 근거는 `app/.local/mission-live-smoke/retry-tool-*.jsonl`에 있다. 실제 장치·DB 저장과 표본의 재현율은 확인이 남았다.
- [PRD 4.3](../PRD.md#43-교정과-다시-말하기), [DEC-092](../DECISIONS.md#dec-092), [TASKS B-04·B-09](../TASKS.md#첫-학습-흐름과-기능-구현)의 교정·재생 근거와 작업 상태를 대조했다. 실패·건너뛰기의 유효한 보고가 재생 뒤 반영되는 단위 시험을 추가했다. `npm test` 20개 파일 181개, `npm run typecheck`, `git diff --check`를 통과했다.

## 미션 연습 재시도 기록의 교정 연결

- 합성 이벤트로 첫 교정을 건너뛴 뒤 새 교정의 도구 원문이 입력 전사와 달라 누락되는 경우를 재현했다. 다음 응답이 성공을 보고하자 기존 기록기는 이미 건너뛴 교정에 시도를 붙였다. 교정과 시도의 원문 불일치는 앞선 Live 시험에서 관찰했으며, 두 교정을 이 순서로 넣은 회귀 사례는 합성이다.

- 변경 전 회귀 시험에서 오연결을 재현했고 변경 뒤 앱 기록과 분리형 재연결 후 다음 모델 요청에서 오연결이 없는지 확인했다. `npm test` 20개 파일 183개, `npm run typecheck`, `git diff --check`를 통과했다. 실제 공급자·장치·DB 검증은 추가 실행하지 않았다.
- [PRD 4.3](../PRD.md#43-교정과-다시-말하기)·[DEC-092](../DECISIONS.md#dec-092)·[TASKS B-04·B-09](../TASKS.md#첫-학습-흐름과-기능-구현)를 대조했다. 시도 1회와 재생 근거 수용 기준은 기존과 같고 두 작업 모두 진행 중이다. [PROGRESS](../PROGRESS.md#다음-재개-지점)와 [CHANGELOG](../CHANGELOG.md#2026-11-18)에 연결했다.

### 격리 DB 복구와 시간 경계

- Node 24.22.0, Docker PostgreSQL 16.15 두 인스턴스, 합성 데이터 환경. 임시 DB의 2번 스냅샷은 커밋하고 지속 DB 확정을 강제로 실패시킨 뒤 클라이언트 메모리 소실을 모의했다. 재개 시 1번까지 복원됐지만 다른 본문의 2번 저장과 3번 저장이 모두 충돌했다. 1번의 기록으로 종료·노트 생성·원문 삭제는 가능했다.
- 계정 행 잠금으로 재개와 기한 작업의 순서를 제어했다. 24시간 직전에는 기존 세션을 재개했다. 기한이 지난 뒤 재개가 먼저 잠금을 얻으면 `SESSION_CLOSING`, 기한 작업이 먼저 종료하면 다음 시작은 새 세션이었다. 만료 세션은 다시 열리지 않았고 늦은 저장은 거절됐다.
- 탈퇴 전에 만든 실제 백업을 복원한 뒤 기존 인증 무효화를 적용했다. 이전 세션은 거절됐지만 새 합성 이메일 로그인으로 탈퇴 계정과 노트가 다시 나타났다. 복원 전에 삭제 상태를 다시 적용하는 절차는 아직 필요하다.
- 저장 중 사용 중인 지속 DB 연결을 끊자 Node가 처리되지 않은 `pg` 오류 이벤트로 종료됐다. 각 풀의 사용 중인 연결에도 오류 처리를 추가한 뒤 요청만 실패하고, 같은 순번·본문이 동일 프로세스에서 저장되는 것을 확인했다. 두 DB 풀의 연결 강제 종료를 서버 회귀 시험에 추가했다. [트러블슈팅](../TROUBLESHOOTING.md#2026-11-18--저장-중-db-연결-종료로-node-프로세스-종료)

### 로컬 동시 세션 지연과 장애 주입

- Next.js 프로덕션 빌드, Node 24.22.0, 격리 PostgreSQL 16.15 두 인스턴스. 합성 계정의 음성 세션 시작·스냅샷 저장 8회·종료를 동시 1·8·16세션에서 각 1회 실행했다. 총 HTTP 250건이 성공했다. 저장 p95/p99는 각각 21.17/21.17ms(8건), 50.12/52.83ms(64건), 71.67/72.92ms(128건)였다. 로그인 준비 시간, 외부 공급자 호출, 브라우저 장치, 자원 계측은 측정 구간에 포함하지 않았다.
- 격리 원문 DB의 신규 연결을 차단하고 기존 연결을 끊었다. 저장 HTTP 요청은 11ms에 503을 반환했다. 연결 복구 후 동일한 저장은 16ms에 200으로 확정됐고, 같은 요청을 다시 보내도 확정 순번은 그대로였다. 두 값은 단일 장애·복구 표본이다.
- 별도 프로세스에서 분리형 어댑터와 재생 조정기에 가짜 STT·LLM·TTS·출력 장치를 연결했다. 동시 1·8·16개로 200회 재현해 첫 오디오 생성과 끼어들기 취소, 다음 응답의 재생 확인을 모두 관찰했다. 동시 16개 128회에서 입력 확정→첫 오디오 이벤트와 끼어들기 이벤트→재생 중단 콜백의 p99는 0.391ms와 0.089ms였다. 이 값은 앱 내부 이벤트 처리만 측정했다. 실사용 응답 지연, 공급자 한도, 실제 오디오 중단, 운영 용량 기준은 남아 있다.
