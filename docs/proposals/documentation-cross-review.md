## 1. 학습 상태 책임과 다시 말하기 보장

근거: DEC-003/008, PRD 6절·F-05, B-03/04/09, 학습 상태 쟁점 L1~L4.

- **추천·이유:** 앱이 확인된 상태와 전이 권한을 보유하고, AI는 대화·교정·재시도 평가를 제안한다. 구조화 이벤트를 앱이 검증·수락하며, 교정/재시도 구간에는 다음 대화로 넘어가는 음성이 재생되기 전 제어하는 작은 계약을 실험한다. 별도 모델로 모든 턴을 재분류하는 구조를 기본값으로 정하지 않는다. 상태 순서를 통제할 수 있다는 것과 언어 평가가 정확하다는 것은 별개다.
- **대안·탈락 이유:** AI 전담은 채택된 앱 상태 관리·복구와 충돌한다. AI 진행을 기록만 하는 안은 위반을 사후 탐지해 F-05를 보장하지 못한다. 전면 분류·버퍼 검사는 지연·오분류·비용을 늘릴 수 있다.
- **남은 불확실성:** 자연스러움과 사전 제어의 교환관계, 교정 음성과 이벤트 순서, 자동/수동 응답 전환 경쟁 조건. 수동 응답 시작만으로 한 응답 안의 금지 질문이 사라진다고 가정하지 않는다. 자동 응답을 끄는 경우에도 끼어들기·재생/생성 취소는 유지해야 한다.
- **검증·재검토:** 교정 중 끼어들기, 실패 재시도, 교정과 다음 질문이 섞인 응답, 이벤트 지연·재연결에서 다음 질문 누출·상태 복구·첫 가청 응답 지연을 평가한다. 제어가 요구사항과 허용 지연을 함께 충족하지 못하면 제어 범위를 재설계한다. F-05를 프롬프트 준수 목표로 완화하는 안은 명시적 재동의 대상이다.

PROGRESS의 포괄적인 책임 미정 표현은 채택 결정과 세부 미정을 섞는다. 큰 책임은 확정, 강제 방식은 미정으로 구분할 것을 제안한다. B-00의 가짜 상태 흐름은 D-04 승인 후 진행할 수 있고 실제 음성의 제어 기법을 확정했다는 증거로 쓰지 않는다.

## 2. 기록·재생 확인·복구와 노트 근거

근거: PRD 6·8절, F-01/04/09/10, B-02/05/06, V-02.

- **추천·이유:** 실제 저장 단계에서는 확인 턴·교정·취소·재생 확인·체크포인트를 서버에서 순차 저장한다. 생성 완료, 장치 재생 확인, 노트에 사용할 근거 확정을 구분하고 요청/응답 ID·연결 세대·버전으로 중복·늦은 사건의 상태 변경을 막는다. 늦은 비용 정산 사건까지 폐기하지는 않는다. L4는 저장된 확인 기록을 입력으로 근거 ID를 연결한 초안을 생성·검증한다. 공급자 맥락이 틀렸으면 확인 요약 추가만으로 고쳐졌다고 보지 않고 실제 제거 또는 확인 기록에서 세션 재구성을 검증한다. 공급자 재개와 새 세션 복구의 지연·누락·재과금도 비교한다.
- **대안·탈락 이유:** 종료 때만 수신하면 탭 종료·끊김·한도 중단으로 유실된다. 모든 음성/토큰 조각 저장은 비용·개인정보 처리량에 비해 이점이 불분명하다. AI 기억만으로 쓰는 노트는 근거 검증이 어렵다.
- **남은 불확실성:** 부분 재생된 발화의 정확한 문장 근거, 전사 오류, 기기의 재생 보고 정확도. OpenAI의 오디오 절단은 정확한 부분 전사문을 제공하지 않는다. 따라서 확인 불가능한 부분 문장은 노트에서 제외하고 잘린 교정은 보류 후 재전달하는 보수적인 안을 권한다. 기기 재생 확인은 사람의 청취·이해를 증명하지 않는다. [OpenAI 대화 관리](https://developers.openai.com/api/docs/guides/realtime-conversations)
- **검증·재검토:** 저장 직전 실패·취소 후 전사 완료·순서 역전·브라우저 종료·재개로 유실/중복 범위를 확인하고, 근거 ID 유효성과 실제 의미를 함께 평가한다. 보수적 제외가 학습 UX를 크게 해치면 별도 정렬·사용자 확인 방법의 비용과 데이터 영향을 비교한다.

일일 노트는 계정 기본 시간대와 세션 시작 시점에 고정한 시간대를 비교해 사용자와 귀속 규칙을 합의한다. 날짜별 원문 집합과 버전으로 재계산하여 동시 생성의 오래된 결과 덮어쓰기를 막고, 세션 삭제 시 파생 노트·복습도 제거/재계산한다. 이미 내려받은 파일은 서비스가 회수할 수 없다. 새로운 예문과 실제 발화를 구분하는 방식은 V-02의 현재 문구와 먼저 맞춰야 한다. 보관·삭제·시간대 정책은 아직 승인되지 않았다.

## 3. 실시간 공급자·연결·맥락·비용 중단

근거: DEC-008, PRD 9.2, D-03, B-09, O-03/07.

- **추천·이유:** 공급자 두 곳의 한 모델씩 필수 계약을 먼저 선별한 뒤 선택 후보 안에서 모델별 품질·비용을 비교한다. OpenAI Realtime 2.1 계열과 Gemini 3.8 Live는 공개 문서상 후보이며 제품의 이중 공급자 운영을 제안하는 것은 아니다. 직접 오디오 연결+서버 인증/제어를 첫 가설로 두고, 강제 통제와 기록 정합성이 실패하면 서버 중계를 비교한다.
- **대안·탈락 이유:** 가격표만 보고 선정하면 교정·취소·재개·접근 조건을 놓친다. 단계별 STT→텍스트→TTS를 기본안으로 바꾸면 채택된 실시간 방향을 재논의해야 한다. 전체 프록시를 선결정하면 서버 부하·비용을 검증 전에 떠안는다.
- **남은 불확실성:** 실제 계정의 모델/한도, 한국어 화자의 교정 품질, 재연결/취소 과금, 악의적 클라이언트와 복수 연결의 차단. 단기 토큰은 장기 키 보호 수단이며 앱 비용 상한의 증거가 아니다.
- **검증·재검토:** 예산·데이터 범위를 승인한 뒤 합성 시나리오로 응답/중단 지연, 교정/질문 규칙, 재생 범위, 연결 교체, 비용·동시 연결을 비교한다. 소표본 선별 실험으로 출시 p95·신뢰성을 주장하지 않는다. 필수 계약을 통과하지 못하면 저렴해도 제외한다.

진행자가 추가 확인한 사실: OpenAI의 `POST /v1/realtime/calls/{call_id}/hangup`은 WebRTC와 SIP 종료를 명시한다. 따라서 서버 종료 수단 자체가 없거나 확인 불가능하다는 결론은 채택하지 않는다. 다만 `200 OK`는 종료 절차 시작이며 실제 무음·과금 중단까지의 지연과 우회 방지는 실측해야 한다. [Hang up API](https://developers.openai.com/api/reference/resources/realtime/subresources/calls/methods/hangup), [종료 동작 안내](https://developers.openai.com/api/docs/guides/voice-sip?voice-api=realtime)

맥락은 고정 규칙·현재 대기 교정·최근 확인 턴·짧은 학습 정보·관련 복습 순으로 관리한다. 공급자 컨텍스트 한도를 서비스 예산으로 쓰지 않고 요약/선택 후 상한을 정한다. 신규 시작은 예산을 사전 확인하고 진행 중 한도 도달은 체크포인트를 남긴 **이용량 일시 중단**으로 표시하는 안을 권한다. 학습 자동 종료나 종료 요약 자동 전환은 하지 않는다. 노트용 예산 예약·중단 뒤 재개 조건·초과 여유분·가격/포함량은 별도 승인 대상이다. 전체 예산이 없으면 노트 호출을 자동 예외 처리하지 않고 명시적 종료 후 생성 대기·재시도를 안내하는 대안도 비교한다.

## 4. 인증·보관·삭제·공급자 이용 조건

근거: DEC-002/008, PRD 8절, D-02, B-01/05, V-03.

- **추천·이유:** 관리형 인증을 우선 비교하되 제품은 미선정으로 둔다. 서버 인증 주체로 계정 소유권을 검증하고 저장/조회뿐 아니라 실시간 토큰·재개·비용·다운로드·백그라운드 노트까지 격리한다. 원본 음성 버퍼, 전사, 교정, 노트, 백업, 운영 로그, 공급자 처리의 보관·삭제 표를 실제 사용자 데이터 전에 승인받는다.
- **대안·탈락 이유:** 자체 비밀번호/복구는 현재 필요에 비해 보안·운영 책임을 늘린다. 출시 직전 정책 일괄 결정은 저장 구조·삭제 파생물을 되돌리는 비용이 크다. 로컬 파일만으로는 계정별 기기 간 기록 요구를 충족하지 못한다.
- **남은 불확실성:** 보관 기간·지역·개별 삭제·대상 연령·계정 복구·국외 처리 조건. API 학습 미사용과 무보관은 다르다. OpenAI 기본 abuse 로그와 ZDR 승인 조건, Gemini 유료 처리의 안전 목적 로깅을 따로 확인해야 한다. [OpenAI 데이터 조건](https://developers.openai.com/api/docs/guides/your-data), [Gemini 이용 조건](https://ai.google.dev/gemini-api/terms)
- **검증·재검토:** 계정 A의 모든 ID/URL/재개 토큰을 B로 재사용해 거부되는지 시험한다. 삭제와 동시 요약·캐시·백업 복원 뒤 기록이 되살아나는지도 검증한다. 지역·삭제·대상 사용자 조건을 만족하지 못하면 공급자/인증/저장 제품을 바꾼다.

새로 발견한 후보 자격 조건: Gemini Developer API 약관은 개발자의 18세 이상 요건과 18세 미만을 대상으로 하거나 그들이 접근할 가능성이 큰 서비스에 대한 제한을 명시한다. Talkie 문서에는 연령 정책이 없다. 일반 고객 대상이라는 설명만으로 충족했다고 볼 수 없으며, 성인 범위·실제 접근 통제·약관 적합성을 공급자 선정 전에 검토해야 한다. OpenAI의 미성년 이용 조건 및 국내 법적 적합성은 이번 검토에서 확정하지 않았다. [Gemini Age Requirements](https://ai.google.dev/gemini-api/terms)

## 5. 최소 기술 스택과 운영 결정 순서

근거: DEC-006/007, D-04/05, initial-stack, O-01/04~08.

- **추천·이유:** 첫 가짜 흐름에는 Next.js+TypeScript 한 앱을 조건부 추천한다. 화면·순수 상태 규칙·공급자 어댑터·기록 경계를 나눠 음성 서버 분리와 공급자 변경 비용을 줄인다. 이유는 초기 실행 프로젝트·언어·계약 수를 줄이는 생산성 추정이며 프레임워크 성능 우위 실측은 아니다.
- **대안·탈락 이유:** Vite+Node는 거의 동등한 후보다. 동일 출처로 배포할 수 있으므로 CORS나 독립 배포 부담을 필연처럼 평가하지 않는다. FastAPI는 Python 전용 처리나 숙련도 이익이 확인될 때 재검토하며, 지금은 두 생태계를 운영할 근거가 부족하다.
- **남은 불확실성:** 사용자 숙련도, 의존성 호환성, 장기 제어 연결·중계 필요, 실제 배포 부하. Next의 Node/Docker 지원은 특정 플랫폼·서버리스의 비용/연결 적합성을 보장하지 않는다. [Next 배포](https://nextjs.org/docs/app/getting-started/deploying)
