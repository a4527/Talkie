# 첫 카페 미션의 최소 API·저장·평가/노트 호출 계약 검토안

작성일: 2026-11-15. 같은 날 Q1~Q4를 결정해 승인된 범위는 [미션 설계의 최소 연결 계약](../design/MISSIONS.md#최소-연결-계약)으로 옮겼다(DEC-086~089). 이 문서는 당시 비교·추천의 기록이며 현행 계약이 아니다. 작성 당시 표현은 **미승인 제안**이었다. [미션 설계의 첫 연결 순서](../design/MISSIONS.md#첫-연결-범위와-구현-순서) 2~4단계를 구현하기 위해 필요한 최소 계약을 비교한다. 제품 약속은 [PRD 4~6절·8절](../PRD.md#4-주요-사용자-흐름), 기존 구현 계약은 [API](../design/API.md)·[DB](../design/DATABASE.md)·[학습 저장](../design/LEARNING-PERSISTENCE.md)·[학습 노트](../design/LEARNING-NOTE.md)를 따른다. 승인 전에는 설계 문서·코드를 바꾸지 않는다.

## 범위와 제외

포함: 직접 제작 카페 미션의 시작 선택(모드·수준), 서버의 정의/버전 고정, 진행 중 미션 상태의 저장·재개, 종료 사유, 종료 후 평가·노트 호출과 결과 저장/조회.

제외(기존 미정 유지): 무진전 운영 임계값(연속 3회는 시험값), 횟수 차감·연결 성립 신호·환급(B-10), 달성 일수의 날짜 귀속·누적/연속 표시·소급(B-12), 수준별 세부 평가표, AI 추천/생성, 노트 분량·상세 교정 보관, 공개 공급자. 아래 계약은 이 값들을 정하지 않고 자리만 분리한다.

## 현재 코드에서 확인한 출발점

- `POST /api/learn`의 `start`는 `scenario`(`correction`·`conversation`·`voice`)만 받고 `learning_sessions.demo_scenario`에 저장한다. 계정당 진행 대화 하나·45초 연결 토큰·24시간 재개·`LEARNING_MODE_CONFLICT`가 이미 있다.
- 원문은 임시 DB `transcript_saves`에 저장 순번별 스냅샷으로 쌓인다. 클라이언트 창은 128 KiB·200턴으로 잘리지만 서버 `readConfirmed`는 확정 순번까지의 모든 저장을 턴 ID로 병합하므로 **전체 대화 재구성은 서버에서 가능**하다. 다만 잘린 미확인 턴은 `hasConversationGaps`로만 표시된다.
- 종료 후에는 `note` 작업이 원문을 읽어 음성 노트를 추출(최대 6청크×30,000자, 2회 시도)하고, 노트 확정 뒤 원문을 삭제한다. 실패 시 종료 후 24시간 안에서 재시도한다.
- 실시간 구조화 도구는 `record_learning_result`(교정/재시도) 하나다. 미션 진행·종료 판단 도구는 없다.

## 추천 계약 요약

| 영역 | 추천 | 주요 대안 |
| --- | --- | --- |
| C1 미션 정의 | 코드 안의 버전 고정 레지스트리(`cafe-wrong-order`, 정의 버전·평가표 버전). 세션에는 ID·버전만 저장 | DB 정의 테이블. AI 생성 미션을 저장할 때 필요하므로 그때 도입 |
| C2 세션 연결 | 지속 DB에 `learning_sessions`와 1:1인 별도 테이블(미션 ID·정의/평가표 버전·모드·수준·종료 사유·최종 경로) | `learning_sessions`에 nullable 열 추가 |
| C3 진행 상태 | 저장 스냅샷에 선택 필드 `missionProgress`를 추가해 같은 저장 순번으로 확정·재개 | 지속 DB에 별도 진행 테이블 |
| C4 실시간 도구 | 두 번째 도구로 경로 제안/수락/확정·무진전 후보를 근거 발화와 함께 보고하고 앱이 검증 | 기존 교정 도구에 필드 병합 |
| C5 종료 후 호출 | 평가 호출과 기존 노트 호출을 **분리**해 같은 작업에서 평가→노트 순으로 실행. 둘 다 확정되면 원문 삭제 | 단일 결합 호출 |
| C6 결과 저장 | 기준별 판정·반점 정수 점수·짧은 사유를 지속 DB에 저장. 보관 기간은 기존 지속 학습 기록(DEC-017)과 같게 둠 | 집계만 장기 보관 등 새 보관 정책 |

아래 절은 각 항목의 근거와 절충이다.

### C1 미션 정의는 코드 레지스트리로 시작

첫 범위는 직접 제작 미션 하나이므로 정의(역할·공개/비공개 정보·처리 조건·경로·목표 항목·배점)와 평가표를 코드의 불변 객체로 두고 `definitionVersion`·`rubricVersion`을 붙인다. 버전을 바꿀 때는 새 객체를 추가하고 기존 버전을 지우지 않는다. 시작 시 서버가 존재·배점 합계(목표 60·언어 40)를 검증하고 세션에 ID·버전을 고정한다. 재개·평가는 저장된 버전으로 정의를 다시 찾는다.

- 장점: 마이그레이션 없이 리뷰 가능한 diff로 정의가 관리되고, 과거 버전이 코드에 남아 소급 재해석을 막는다.
- 한계: AI 추천/생성 미션은 저장할 곳이 없다. F-06 연결 때 DB 정의 테이블을 별도로 설계한다. 이 전환은 세션의 `(미션 ID, 버전)` 참조를 유지하면 호환된다.

### C2 세션의 미션 고정은 1:1 테이블

`learning_session_missions`(가칭): 학습 세션 ID PK·사용자 ID, `(learning_session_id, user_id)` 복합 FK cascade, `mission_id`·`definition_version`·`rubric_version`·`mission_mode`(`practice`·`real`)·`language_level`(`A1`·`A2`·`B1`·`B2`·`C`), 종료 시 채우는 `mission_end_reason`(`goal_completed`·`no_progress_failed`·`user_ended`·`resume_expired`)·`final_route_id`(nullable).

- 미션 세션 생성은 `learning_sessions` 생성과 같은 지속 DB 트랜잭션에서 수행해 미션 없는 진행 세션이 생기지 않게 한다. 기존 자유 대화 행은 건드리지 않고 미션 행이 없는 세션은 구형 세션으로 취급한다(근거 없는 변환 금지).
- 모드·수준 CHECK와 PRD의 “재개 시 저장값 사용·기존 미션 덮어쓰기 금지”는 이 행을 수정하지 않는 것으로 보장한다(종료 사유·최종 경로만 1회 기록).
- 대안(nullable 열)은 조인이 없지만 구형/신규 세션의 조건부 CHECK가 늘고 `demo_scenario`와 의미가 섞인다.
- 음성/텍스트 구분은 기존 `demo_scenario`를 유지한다. 미션 시작은 비공개 음성 시험(`voice`)을 기본으로 하고, 텍스트 가짜 공급자는 자동 시험용으로만 연결한다.

### C3 진행 상태는 저장 스냅샷에 포함

`ConversationSnapshot`에 선택 필드 `missionProgress`를 추가한다. 내용은 확인된 경로 사건 목록(`routeId`·`event: proposed|user_accepted|staff_confirmed|route_changed`·근거 턴 ID)과 무진전 연속 후보 수·근거 턴 ID다. 대화 턴과 같은 저장 순번으로 확정되므로 재개 시 “마지막 저장 확정 상태”와 일치하고, 미확정 진행이 재개 근거가 되지 않는다.

- 무진전 연속 수는 PRD 4.2.2에 따라 재개 시 이어 쓰지 않으므로, 재개 응답에서 서버가 0으로 초기화해 돌려준다.
- 원문과 함께 24시간 뒤 삭제된다. 평가에 필요한 최종 경로는 종료 시 C2의 `final_route_id`로 지속 저장한다.
- 구형 저장 JSON에는 필드가 없으므로 기존 키·해시 호환 규칙(저장 시 키 순서·기본값)을 그대로 따른다. 빈 진행은 직렬화하지 않아 구형 세션 해시가 바뀌지 않게 한다.

### C4 실시간 미션 도구

같은 실시간 AI에 `report_mission_state`(가칭)를 추가한다. 매 턴 별도 심판 호출은 두지 않는다(MISSIONS 설계).

| 입력 | 앱 검증 |
| --- | --- |
| 경로 사건과 `routeId` | 정의에 있는 경로인지, 사용자 수락의 근거 턴이 실제 사용자 발화인지, 직원 확정이 수락 뒤 재생 완료된 상대역 턴인지 |
| `goalCompleted` | 한 경로의 제안·사용자 수락·직원 확정이 모두 확인될 때만 종료 진행. 마지막 짧은 대사 재생 뒤 `end` |
| `noProgress` 후보와 이유·근거 턴 | 실전 모드인지, 근거가 확정된 사용자 발화인지, 제외 사건(빈 전사·미재생 질문·연결 중단·상대역 반복 질문) 뒤 연속성이 끊겼는지, 목표 완료가 우선인지 |

연습 모드는 무진전 필드를 무시한다. 실전 모드에는 교정 도구를 넣지 않는다(PRD 4.3). 임계값은 설정값으로 두고 기본 3을 **시험값**으로만 사용한다. 정확한 함수 이름·필드는 실제 프롬프트 작성 때 확정하며 위 검증 책임만 계약으로 둔다. 분리형 경로도 같은 구조화 결과를 같은 검증기에 넘긴다.

### C5 종료 후 평가와 노트는 분리 호출

종료 작업(기존 `note` 작업 확장)은 원문을 한 번 읽어 다음 순서로 처리한다.

1. **평가 호출:** 고정 정의·평가표·수준 설명, 전체 대화(턴 ID 포함)·교정/재시도·`hasConversationGaps`·최종 경로를 입력한다. 출력은 목표 6항목(`met`·`unmet`·`undeterminable`)과 언어 12기준(`met`·`partial`·`unmet`·`undeterminable`)의 판정·근거 턴 ID·반대 근거·짧은 사유다. 모델 총점은 받지 않는다.
2. **앱 검증·합산:** 근거 턴이 실제 사용자 턴인지, 판정 값이 허용 값인지, 기준이 빠짐없이 한 번씩인지 확인한다. 고정 배점에 매핑해 **반점 정수**로 획득/평가 만점을 계산하고, 80% 판단은 `earned × 10 ≥ max × 8` 정수 비교로 한다. 근거 검증에 실패한 기준은 판정 불가로 낮추지 않고 그 평가 시도를 실패로 보고 재시도한다(근거 없는 판정 불가는 만점을 바꾸기 때문).
3. **노트 호출:** 기존 추출 경로를 그대로 쓴다(DEC-064/065 상한 유지).
4. 평가 결과와 노트를 각각 확정하고, **둘 다 확정(또는 빈 대화로 생략)**된 뒤 원문을 삭제한다. 종료 후 24시간 기한은 그대로이며 기한이 지나면 미확정 평가는 `unavailable`로 기록한다(점수 없음·일수 불인정).

- 분리 이유: 노트 추출은 이미 근거 검증·부분 저장·재시도가 구현·합성 평가됐다. 평가는 출력 구조와 검증이 다르고 실패 처리도 다르다(노트는 부분 저장 허용, 평가는 기준 누락 불허). 결합은 호출 수를 줄이지만 한쪽 실패가 다른 쪽 재시도를 유발한다.
- 비용: 호출이 하나 늘어난다. 실제 비용·지연은 측정 후 결합 여부를 다시 판단한다(B-06의 “품질·비용 검증 후 결정”을 유지).
- 장문: 평가 입력이 노트 상한(약 180,000자)을 넘으면 분할 판정은 하지 않고 `undeterminable` 처리 대신 평가 실패로 기록한다. 첫 카페 미션에서는 도달하지 않을 것으로 추정하며 분할 평가는 후속이다.
- 재개 만료로 자동 종료된 미션도 평가는 수행하되 일수에서 제외하는 표시는 종료 사유로 판단한다.

### C6 결과 저장과 조회

지속 DB `mission_evaluations`(가칭): 학습 세션 1:1·사용자 복합 FK, 상태(`pending`·`ready`·`unavailable`), 목표/언어 영역별 획득·만점(반점 정수)·전체 획득·평가 만점, 달성 여부(만점 0이면 null), 기준별 판정·사유를 담는 검증된 JSON, 평가 호출 버전, 확정 시각.

- 보관 기간은 새로 정하지 않고 기존 지속 학습 기록(DEC-017: 무료 종료 후 30일, 유료 무기한, 탈퇴 시 삭제)과 같게 둔다. 일수 집계가 30일 만료 기록을 어떻게 다룰지는 B-12의 날짜 귀속·소급 결정에서 함께 정한다.
- 사유에는 사용자 발화 원문을 길게 복사하지 않는다. 짧은 인용이 필요하면 노트의 원문 근거 규칙(짧은 근거)과 같은 상한을 쓴다.
- `GET /api/learn`의 세션 항목에 `mission`(ID·모드·수준·종료 사유·최종 경로)과 `evaluation`(상태·표시용 점수 원값)을 추가한다. 표시 문자열·반올림은 화면에서 DEC-080 규칙으로 만들고 저장하지 않는다.

## 시작 API 형태

`POST /api/learn {action: "start", mission: {missionId, missionMode, languageLevel}}`를 추가하고 기존 `scenario` 요청은 그대로 둔다. 둘을 함께 보내면 거부한다.

- 진행 미션이 있으면 기존 재개 규칙을 따르고 **요청의 모드·수준을 무시**하며 저장값을 응답한다. 진행 중인 것이 구형 자유 대화면 `LEARNING_MODE_CONFLICT`로 기존 대화 종료를 안내한다.
- 응답에 사용자 공개 정보(상황·역할·화면 목표·모드·수준)만 담은 `mission`을 추가한다. 상대역 비공개 정보·채점 항목은 브라우저에 보내지 않는다.
- 횟수 확인·차감은 B-10 이전까지 **호출하지 않으며** 기존 시험 시간 보호를 운영 차감으로 표시하지 않는다.

Q2 사용자는 “평가가 끝나면 학습 노트 작성 혹은 학습 노트 작성 후 평가”로 분리 순차 호출을 선택해 평가→노트로 처음 기록했으나, 순서 비교(노트→평가 추천) 뒤 사용자가 “그냥 동시에 호출하는게 좋겠다”로 동시 호출·실패한 쪽만 재시도로 바꿨다(DEC-087). 위 C5의 순차 실행 추천은 채택되지 않았다. Q3은 추천 대신 “점수 집계만 장기 보관”을 선택했다(DEC-088, 위 C6의 단일 보관 추천은 채택되지 않음). Q4 평가 재시도 채택(DEC-089).

C2~C4의 테이블·필드 이름과 도구 형태는 위 결정 안의 구현 계약이므로 승인 후 [미션 설계](../design/MISSIONS.md)·[DB](../design/DATABASE.md)·[API](../design/API.md)에 옮기면서 확정한다.

## 검증 계획(승인 후)

- 자동: 시작 시 버전 고정·재개 시 요청 무시·구형 세션 비변환·동시 시작·스냅샷 해시 호환·진행 사건 검증(허위 근거·순서 위반·연습 무진전 무시)·반점 합산/80% 경계·0 만점·평가/노트 각각 실패와 기한 만료·원문 삭제 순서.
- AI 사례: [합성 평가 사례](FIRST-MISSION-EVALUATION-CASES.md)의 여덟 사례로 판정 후보와 실제 평가 호출 결과를 대조하고 차이를 worklog에 기록한다. 실제 공급자 호출은 무료 비공개 시험 조건 안에서만 하며 표본·비용은 호출 전에 확인한다.
