# API 사용량 한도와 사용자 안내 검토안

후속: 사용자가 비용이 높다고 판단해 [절감 대안 전반](VOICE-COST-REDUCTION.md)을 검토하고 분리형 비공개 시험 경로를 로컬 앱에 통합했다. 아래 $1.25/$38.10/$76.20는 Live 전용 과거 산정안이며 승인된 한도나 두 경로의 공통 상품 한도가 아니다.

작성일: 2026-10-30. 상태: [시간·활동량 방향](#새-방향-검토-시간활동량과-주간-과금-대조)의 B안은 DEC-062로 승인. 앞서 승인된 DEC-060/061의 토큰 집행은 대체됐고 아래 과거 계산·원장/90일 보존 제안은 현행 구현 기준이 아니다. 모델 후보·시간/기간·노트 호출·지출 수치는 미승인이다. 15분은 과거 계산 사례이며 고정 종료 상한이 아니다. 현행 계약은 [PRD](../PRD.md#92-ai-제공맥락이용량-정책)·[음성 설계](../design/VOICE.md#시간-기반-이용과-비용-대조)를 따른다.

## 현재 구현과 기존 합의

- 현재 `/voice`는 연결 전에 Gemini Live와 분리형을 선택한다. Live는 [설정](../../app/src/voice/gemini-live-setup.ts)의 `models/gemini-3.8-live`를 사용한다. 분리형은 [서버 경로](../../app/src/server/voice-cascade.ts)에서 Soniox 실시간 STT, `gemini-3.5-flash-lite` 텍스트 응답, `gemini-3.8-flash-lite-tts` 음성 합성을 연결한다. 둘 다 비공개 시험 경로이며 최종 공급자/모델 선정은 아니다.
- 아래 가격·15분 계산과 $1.25 제안은 **Live 경로만** 가정한 과거 사례다. Live setup에 명시적 맥락 압축 설정이 없고 공급자 사용량 집계도 없다. 분리형은 짧은 사용자 시험에서 전사·응답·재생이 보고됐으나, Soniox STT 사용액 $0.002298 외에 Gemini 텍스트/TTS를 포함한 전체 청구액은 확인되지 않았다([작업 기록](../worklogs/2026-10-30.md#분리형-음성-main-통합)). 두 경로의 세션당 비용과 사용량을 같은 수치로 취급하지 않는다.
- [DEC-058](../DECISIONS.md#dec-058--별도-종료-선별-요청과-제한적-재시도)과 [노트 설계](../design/LEARNING-NOTE.md#생성검증저장-순서)에 따라 종료 노트는 대화 경로와 분리된 LLM 요청으로 만든다. 구체 모델·재시도 수치 등은 미정이다. 대화의 남은 토큰으로 노트를 생성한다는 뜻이 아니다.

## 공식 관찰과 계산 조건

2026-10-30 [Google 가격표](https://ai.google.dev/gemini-api/docs/pricing) 확인: Gemini 3.8 Live의 100만 토큰당 입력 텍스트 $0.75·음성 $3, 출력 텍스트 $4.50·음성 $12. [공식 사용 안내](https://ai.google.dev/gemini-api/docs/live-api/best-practices)는 음성 약 25토큰/초, 턴마다 이전 맥락을 포함한 재과금과 전사 텍스트의 추가 출력 과금을 설명한다. 따라서 음성 분당 요금만 곱한 값은 세션 전체 비용 추정으로 충분하지 않다.

합성 산정 가정: 연결 15분 동안 마이크 900초 전송(22,500토큰), AI 음성 총 360초(9,000토큰), 시스템/초기 맥락 2,000텍스트 토큰, 전사 총 3,000출력 텍스트 토큰. N번 문답에 음성과 발화량을 균등 분배하고 압축·재연결은 없다고 가정한다. 과거 AI 출력 음성도 다음 턴부터 입력 맥락에 포함한다. 도구 교환/내부 추론·실제 무음 처리·초기 맥락 차이는 계산에 완전히 반영하지 못한다.

계산식(USD): `3/1,000,000 × [22,500×(N+1)/2 + 9,000×(N-1)/2] + 12/1,000,000×9,000 + 0.75/1,000,000×2,000×N + 4.50/1,000,000×3,000`.

| 15분 동안 문답 수 | Live 추정 비용 |
| --- | --- |
| 10회 | $0.63 |
| 20회 | $1.12 |
| 30회 | $1.60 |

실측 평균이나 상한 보장값이 아니다. 짧은 문답이 많은 튜터 특성상 턴 수가 핵심 변수다. 실제 공급자 사용량과 청구 대조가 필요하다. 맥락 압축은 비용을 줄일 가능성이 있지만 기억/교육 품질 영향과 실제 절감량은 미확인이며 채택하지 않았다.

## 과거 Live 전용 초기 한도 제안

| 항목 | 제안 | 의미 |
| --- | --- | --- |
| 세션 Live | $1.25 상당 | 20문답 기준 약 $1.12와 여유분. 15분 보장이 아니며 문답이 많으면 더 일찍 소진 |
| 세션 노트 | $0.02 별도 예약 | Live 종료 뒤의 텍스트 LLM 요청과 제한적 재시도용. 마무리 음성 예산은 Live 쪽에 따로 확보해야 함 |
| 하루 1회 수준 구독 | 30일 환산 Live $37.50 + 노트 $0.60 | 합계 $38.10 상당. 판매 가격이나 실제 평균 원가가 아니라 한도 배정 시나리오 |
| 하루 2회 수준 구독 | 30일 환산 Live $75 + 노트 $1.20 | 합계 $76.20 상당. 동일 조건의 두 배 |

구독 실제 갱신 주기·일일 강제 한도·이월 여부는 별도 합의한다. 우선 기간 총량 안에서 날짜별 사용을 유연하게 하는 쪽을 제안한다. 위 월액은 API 예산만이며 세금·환율·결제 수수료·서버·이익은 포함하지 않는다. 저가 구독을 목표로 한다면 이 구조 그대로 확정하기 전에 맥락 압축이나 다른 음성 경로의 비용/품질 검증이 필요하다.

노트 모델의 계산용 후보는 Gemini 3.5 Flash-Lite다(선정 아님). 위 가격표의 Standard 입력 $0.30/100만·출력 $2.50/100만 기준, 입력 12,000·출력 2,000토큰이면 $0.0086, 같은 최대 크기 두 요청이면 $0.0172다. 출력에는 추론 과금분도 포함해 예산을 관리해야 한다. 따라서 $0.02를 초기 예약 제안으로 둔다. 12,000토큰이 실제 15분 원문에 충분한지·품질은 미확인이며 초과 원문을 조용히 자르는 정책은 채택하지 않는다. 이 계산으로 재시도 횟수나 기존 기한 내 재시도 정책을 확정하지 않는다.

## 사용자에게 보여줄 것

토큰·달러·백분율 대신 대화 중에는 경과 시간과 마무리 단계만 표시하는 안을 추천한다. 내부 예산이 마무리 예약분 경계에 접근하면 ‘이번 연습을 마무리할게요’로 전환하고, 마지막 답변과 종료를 위한 제한된 사용량을 남긴다. 몇 분/몇 문답이 남았다고 보장하지 않는다. 마무리 예약분의 구체 크기는 응답 한도와 실측으로 정해야 한다.

과거 Live 산정 당시에는 시작 화면에 ‘보통 15분 안팎으로 연습해요’와 평균 세션 소비량으로 환산한 ‘약 N회 분량’을 표시하는 대안도 검토했다. 15분은 현행 종료 한도가 아니며 분리형의 평균 이용량도 없다. 두 경로의 실측 전에는 이 수치를 사용자 안내로 채택하지 않는다. ‘매일 1회’처럼 고정 횟수를 보장하려면 서비스가 비용 변동을 부담하는 별도 상품 정책이 필요하다.

## 다음 결정 검토: 집계·경계·안내

2026-10-30 당시 승인: 사용자가 아래 다섯 항목의 A안을 모두 선택했다(DEC-061). 이 표는 당시 대안·절충의 기록이며 DEC-062가 토큰 집행을 대체했다. Live와 분리형의 과금 토큰 종류·단가가 다르므로 동일한 숫자의 원시 토큰을 같은 비용으로 볼 수 없다는 조사 결과는 유지한다. 현행 계약은 PRD와 음성 설계를 따른다.

| 논의 | 채택안과 당시 대안 | 사용자·비용·구현 영향 |
| --- | --- | --- |
| 1. 사용량 집계 단위 | **A 채택:** Live는 입력/출력 음성·텍스트, 분리형은 Soniox STT·Gemini 텍스트·TTS의 공급자 과금량을 각각 기록하고 단가를 반영한 정규화 사용량으로 세션/기간 한도를 차감한다. 실제 청구액도 경로별로 대조한다. **B:** 모든 토큰을 1:1 합산한다. | A는 같은 토큰 수라도 음성 출력 등의 큰 비용 차이를 반영한다. 공급자별 측정 항목·단가 변경·모델 교체 때 환산 기준을 관리해야 하며 사용자가 토큰 숫자를 직관적으로 이해하기 어렵다. B는 집행이 단순하지만 발화·교정·재시도가 끊길 수 있다. 예약도 실제 비용의 절대 상한은 아니므로 늦은 사용량 보고·연결 중단의 오차를 측정해야 한다. |

| 4. 노트 예약·실패 | **A 채택:** 대화 시작 때 별도 노트 예산을 예약하고 종료 뒤 실제 사용량으로 정산한다. 노트 실패는 기존 24시간 안에서 예약 잔량과 정한 재시도 한도 안에서 처리하고 부족/실패를 명시한다. **B:** 종료 시점에만 노트 예산을 확인한다. | A는 긴 대화·기간 소진 뒤에도 노트 생성 기회를 보호하지만 미사용 예약의 해제·정산과 재시도 상한이 필요하다. B는 원장 구현이 간단하지만 종료 시 노트가 빠질 가능성이 커진다. 실제 근거 없는 시험용 노트로 자동 완성하지 않는 DEC-058을 유지한다. |
| 5. 사용자 안내 | **A 채택:** 시작 전 현재 기간의 이용 가능 상태·갱신일·사용 방식에 따라 변동됨을 보여주고, 대화 중에는 ‘마무리 단계’만 안내한다. 실측 전 남은 분/횟수는 제시하지 않는다. **B:** 토큰 잔량 또는 평균 기반 예상 분/횟수를 항상 표시한다. | A는 잘못된 시간·횟수 보장을 피하지만 남은 양의 직관성이 낮다. B는 계획하기 쉽지만 누적 맥락·질문 수에 따른 편차가 커서 예측 정확도·갱신 시점을 함께 관리해야 한다. 실제 사용자 시험 뒤 표시 방식을 조정할 수 있다. |

집행 전 확인: Live 직접 연결의 공급자 사용량 보고 시점과 서버 집행 가능성, 분리형 Soniox 연결과 서버의 텍스트/TTS 요청별 과금량·중단 시 비용을 각각 확인한다. 공급자 보고가 늦거나 누락되면 예약/최대 응답·연결 길이 안전장치만으로 허용 오차를 충족하는지 경로별로 측정한다. 충족하지 못하면 해당 경로·한도 집행 방식을 다시 논의한다. 위 추천은 두 경로의 집행 가능성이나 공급자 적합성을 검증한 결과가 아니다.

## 직접 연결 집행 가능성 조사

2026-10-30 공식 문서와 현재 코드를 대조한 정적 조사이며 실제 호출·청구 측정은 하지 않았다.

| 경로 | 확인한 사실 | 서버 집행에 대한 추정과 미확인 |
| --- | --- | --- |
| Gemini Live | [Live WebSocket API](https://ai.google.dev/api/live)는 서버 메시지의 `usageMetadata`와 입력/출력 종류별 토큰 수를 정의한다. [임시 토큰 안내](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens)는 브라우저가 공급자에 직접 연결하며 단일 새 세션·만료와 설정 제약을 줄 수 있다고 설명한다. 현재 토큰 발급은 `uses: 1`, 만료 및 setup을 설정하고, 브라우저 어댑터가 WebSocket을 받는다. | 사용량 메타데이터는 현재 브라우저에 도착하므로 서버 원장의 독립 검증 근거가 아니다. 토큰 만료는 발급 단위의 시간 경계이며 각 응답 전에 세션/기간 잔여량을 원자적으로 확인하고 생성 중 차단하는 기능으로 확인되지 않았다. 실제 메시지별 보고 시점·누락·중단 뒤 청구와 서버에서 조회 가능한 세션별 사용량은 미확인이다. |
| Soniox STT | [사용 기록 안내](https://soniox.com/docs/guides/usage-logs)는 완료 요청의 비용·토큰·음성 길이와 서버가 임시 키에 묶을 수 있는 `client_reference_id`를 설명한다. 현재 임시 키는 단일 사용·세션 시간 상한으로 발급하고 브라우저가 STT WebSocket을 연다. | 식별자를 무작위 연결 ID에 묶으면 사후 대조에 쓸 가능성이 있지만, 현재 발급 요청에는 식별자가 없고 지속 원장도 없다. 사용 기록은 완료된 요청에 한정되므로 응답 전 예약이나 연결 중 잔여량 판정의 근거가 될 수 없다. 조회 지연·중단 요청의 과금 반영·세션 시간 상한의 실제 동작은 미확인이다. |
| 분리형 Gemini 텍스트/TTS | 현재 두 `generateContent` 호출은 서버에서 수행해 응답을 받지만 `usageMetadata`를 읽거나 저장하지 않는다. 텍스트는 `maxOutputTokens`를 설정하고 TTS는 생성 문구와 반환 음성 크기를 제한한다. | 서버 측 요청별 예약·정산을 붙일 위치는 있다. 실제 종류별 과금량, 실패·취소 뒤 청구, TTS의 최대 과금량과 청구 대조는 아직 확인되지 않았다. |

다음 검증 순서: (1) 합성 입력으로 경로별 응답 메타데이터와 완료/중단/재연결 시점, Soniox 사용 기록의 도착 지연을 민감 원문 없이 측정한다. (2) 서버 예약만으로 신규 호출과 진행 연결의 비용을 제한할 수 있는지 동시 탭·프로세스 재시작을 포함해 확인한다. (3) 직접 연결에서 허용 오차를 충족하지 못하면 서버 중계와 경로 제한의 지연·운영비·데이터 접근 영향을 비교해 후속 동의를 구한다. 수치 한도와 상품 약속은 측정·경로 결정 전에는 확정하지 않는다.

2026-10-30 당시 후속 합의: 초기 차감은 공급자 과금량과 단가를 기준으로 삼고, 운영 중 실제 청구·이용 패턴에 맞춰 Talkie 환산식을 조정하기로 했다(DEC-061 후속). 이 토큰 차감은 DEC-062로 대체됐다. 분리형 경로가 Live보다 얼마나 저렴한지는 Soniox STT 일부 사용액만으로 확정할 수 없다는 미확인 상태는 유지한다.

### 다음 실측 준비: 직접 연결의 집행 오차

현재 코드를 다시 확인했다. 분리형 Gemini 텍스트/TTS의 `generateContent` 응답은 서버에서 받지만 `usageMetadata`는 아직 읽지 않는다. Live와 Soniox STT는 브라우저가 공급자 WebSocket을 직접 열어 서버가 응답별 사용량을 관찰하지 못한다. 현재 단일 프로세스의 연결/요청 횟수 제한은 지속 예약이나 재시작 후 차단 근거가 아니다. 아래는 **전체 집행 검증의 절차**이며 일부 제한 계측 결과는 뒤에 구분해 적었다. 경로 변경·한도 수치·로그 보존 정책의 승인이나 구현 완료를 뜻하지 않는다.

1. 합성 발화로 두 경로를 각각 짧은 정상 종료, 발화 중 취소, 네트워크 단절, 재연결의 네 조건에서 시험한다. 시작/종료 시각, 익명 시험 연결 ID, 공급자/모델/종류별 과금량, 메타데이터 수신 시각과 사후 청구 확인 시각만 남긴다. 원문·음성·임시 키·API 키는 기록하지 않는다. 실제 호출 전에는 시험 횟수와 지출 상한을 정한다.
2. 분리형 Gemini는 서버 응답의 종류별 과금량과 실패/취소 응답의 보고 여부를 확인한다. Soniox는 임시 키와 무작위 연결 ID를 연결하는 `client_reference_id` 후보가 완료 요청 사용 기록에서 조회되는지, 언제 도착하는지 확인한다. Live는 브라우저 메타데이터의 시점·누락과 서버에서 같은 세션의 사용량을 독립 조회할 수 있는지를 분리해 기록한다. 브라우저가 보낸 값은 집행의 독립 증거로 간주하지 않는다.
3. 각 조건에서 마지막 서버 승인 뒤 공급자가 추가로 과금한 양을 모델·종류별로 계산한다. 보고 지연 중 최대 미확정 사용량, 예약 상한을 넘은 양, 공급자 청구와 수집량의 차이를 따로 보고한다. 취소·중단의 청구가 나중에 나타나면 원래 연결에 귀속해 다시 대조한다. 표본 수와 청구 확인 시각을 함께 남기고 청구가 미확인인 경우 오차를 확정하지 않는다.
4. 같은 계정의 두 탭과 프로세스 재시작을 합성/로컬 시나리오로 시험해 신규 요청 차단의 우회 가능성을 확인한다. 실제 공급자 측정과 로컬 경합 시험의 결과를 섞어 성공 판정하지 않는다.

판단 순서는 경로별로 (a) 서버 독립 사용량 확인 가능 여부, (b) 예약만으로 연결 중 초과를 제한할 수 있는지, (c) 사후 청구와 차감량의 오차 순이다. 직접 연결에서 확인 불가 또는 허용 오차 초과가 드러나면 서버 중계, 해당 경로의 비공개 시험 유지/제외를 비교한다. 중계는 서버가 흐름을 통제할 여지가 있지만 사용자 음성/전사의 서버 경유, 지연·대역폭·운영비 증가가 있다. 경로 제외는 집행 복잡도를 줄이지만 선택권과 음성 품질/비용 대안을 줄인다. **허용 오차·최종 경로와 데이터 처리 변경은 실측 뒤 별도 논의한다.**

2026-10-30 제한된 실제 호출 결과: 사용자의 요청으로 Gemini 텍스트·TTS·Live 각 1회와 Soniox 정상 종료·중단 각 1회를 합성 입력으로 확인했다([조건과 결과](../worklogs/2026-10-30.md#실제-공급자-사용량-보고-시험)). 서버의 Gemini 텍스트/TTS 응답에는 사용량 메타데이터가 왔고, Live 직접 연결에서는 클라이언트가 사용량 메시지 1개를 받았다. Soniox 정상·중단 연결은 모두 사후 사용 기록에 나타났지만 종료 약 2초 뒤 첫 조회에서는 없었다. 따라서 Soniox의 완료 메시지 유무만으로 과금 여부를 단정할 수 없고, 사후 기록을 새 응답의 즉시 예약 근거로 사용할 수도 없다. 이 표본은 비용 상한·보고 지연 상한·서버 독립 집행을 입증하지 못한다. 재연결·동시성·청구서 대조는 남는다.

### 과거 구현 검토: 원장 경계와 순서

당시 분리형 텍스트·TTS는 서버에서 `generateContent`를 호출하지만 응답의 `usageMetadata`를 버렸다. Live와 Soniox STT는 브라우저 직접 연결이다. 연결 토큰과 요청 횟수는 서버 메모리의 `Map`에 있어 재시작과 다중 인스턴스에서 예약 근거가 될 수 없다. 당시 순서는 **기존 서버 호출의 종류별 계측 → 지속 원장의 중복 방지·환산식 버전 → 예약/정산의 경합 시험 → 직접 연결의 미확정 사용량 측정 → 경로별 집행 방식 결정**으로 제안했다. 이 순서는 DEC-062 채택으로 중단됐으며 B-10의 현재 완료 기준이 아니다.

| 남은 경계 | 제안과 확인할 근거 | 절충·영향 |
| --- | --- | --- |
| 원장의 소유·수명 | 기존 지속 DB에 사용자·학습 세션·기간과 요청별 예약/사용 사건을 연결하고, 동일 공급자 요청/재시도/늦은 보고를 한 번만 정산하는 키를 둔다. 원장 보존 기한은 인증·학습 기록의 기존 기한과 대조해 별도 합의한다. | 재시작·동시 탭에서도 단일 잔여량을 판정하기 쉽지만 DB 경합·마이그레이션·탈퇴 삭제 범위가 늘어난다. 보존 기간을 정하지 않고 영구 보관하지 않는다. |
| 증거의 출처 | 서버가 받은 Gemini 텍스트·TTS 메타데이터를 먼저 수집한다. 브라우저 Live 보고는 잠정 값으로 표시하고, Soniox의 무작위 `client_reference_id` 사용 기록은 원래 연결에 사후 연결해 대조한다. | 서버 측 부분 경로는 먼저 검증할 수 있지만 직접 연결의 즉시 잔여량은 확정할 수 없다. 브라우저 값만으로 사용자 한도를 확정하면 우회·누락 위험이 있다. |
| 예약과 누락 보고 | 요청을 보내기 전에 동일 트랜잭션에서 세션·기간 잔여량과 노트 예약을 검사한다. 취소/실패 후 공급자 과금이 미확인인 사건은 즉시 0으로 지우지 않고 미확정 상태로 유지하며 사후 기록과 대조한다. 미확정 예약 해제 시점과 최대 응답·마무리분은 측정 후 정한다. | 과다 차감이나 이용 대기와 초과 비용 사이의 절충이다. 해제 시점을 너무 앞당기면 늦은 청구가 한도를 넘고, 무기한 유지하면 사용 가능한 잔여량이 묶인다. |
| 환산식 변경 | 공급자·모델·종류별 관측량과 적용 환산식 버전/시각을 함께 남기고 새 사건부터 새 버전을 쓴다. 사후 공급자 정정은 원래 사건에 연결해 차이를 기록한다. | 과거 차감이 바뀌지 않고 청구 대조가 가능하지만 가격 변경·모델 교체 때 버전 운영이 필요하다. 실제 단가·정규화 기준은 경로별 측정 전 확정하지 않는다. |
| 직접 연결의 공개 집행 | Live와 Soniox 각각 서버 독립 확인 가능성·보고 지연 중 초과량·취소 청구를 측정한 뒤 직접 연결 유지, 서버 중계, 비공개 시험 유지 중 선택한다. | 중계는 연결 통제를 늘리지만 지연·대역폭·운영비와 음성/전사의 서버 경유가 생긴다. 직접 연결은 현재 지연 경로를 유지하지만 집행 가능성을 아직 입증하지 못했다. |

첫 구현 단위는 공급자 호출의 상태·모델·종류별 사용량만 민감 원문 없이 파싱하고, 정상·오류·취소 응답에서 메타데이터 유무를 구분하는 것이다. 이 계측만으로 세션/기간 한도나 청구 대조가 동작한다고 표시하지 않는다. 원장 보존 기한·미확정 예약 해제 기준·직접 연결의 허용 초과 오차와 경로 변경은 실제 측정과 별도 동의가 필요한 결정으로 남긴다.

후속 구현 상태: 분리형 Gemini 텍스트·TTS 응답에서 수치만 추출하는 함수와 선택적 서버 관찰자 경계를 추가했다. 현재 라우트는 관찰자를 연결하지 않으며 원장 저장·예약/정산은 없다([작업 기록](../worklogs/2026-10-30.md#서버-gemini-사용량-추출-경계)).

<a id="다음-결정-검토-원장의-보존과-미확정-사건"></a>

### 철회된 검토: 원장의 보존과 미확정 사건

DEC-061 당시 서버 원장·중복 없는 정산을 승인했지만 원장 보존 기간과 미확정 예약 해제 시점은 정하지 않았다. 이 검토는 DEC-062의 시간 이용권 채택으로 철회됐다. 아래 30/90일은 승인된 보존 기한이 아니다. [기존 DB](../design/DATABASE.md#저장소와-스키마-경계)의 학습 세션/노트는 계정 탈퇴 때 연쇄 삭제되고 무료 노트는 학습 종료 후 30일에 만료한다. [PRD 8절](../PRD.md#8-저장-데이터와-학습-노트)의 원문 기한은 비용 메타데이터 보존 기한이 아니다.

Google 공식 안내 기준, [AI Studio의 Usage 대시보드](https://ai.google.dev/gemini-api/docs/billing/)에서 Gemini API 사용량을 볼 수 있고 Prepay 잔액 차감은 거의 실시간이다. [Cloud Billing 비용 상세](https://docs.cloud.google.com/billing/docs/how-to/resolve-issues)는 보통 하루 안에 나타나지만 24시간을 넘길 수 있고, 결제 계정의 차감이 상세 보고보다 먼저 보일 수도 있다. 따라서 당일 비용 확인 가능성과 요청별 최종 청구액 확정은 다르다. 90일은 이 보고 지연 때문에 필요한 최소 기간이 아니며, 이후의 정정·대조에 얼마의 이력이 필요한지를 따로 판단하는 제안값이다.

| 선택 | 추천안 A | 대안 B | 영향과 확인할 점 |
| --- | --- | --- | --- |
| 사용 사건·기간 합계 보존 | **A 제안:** 원문 없는 요청별 사용/예약 사건과 기간 합계를 해당 이용량 집계 기간 종료 후 90일까지만 지속 DB에 보관하고, 기한 경과 시 삭제한다. 계정 탈퇴 시에는 이 기한을 기다리지 않고 기존 삭제 기한 안에 함께 삭제한다. | 집계 기간 종료 후 30일만 보관하거나 학습 세션·노트의 만료에 맞춰 함께 삭제한다. | 90일은 사후 정정·대조에 여유를 주지만 30일보다 메타데이터 보관과 저장/정리 비용이 늘어난다. 30일은 더 짧지만 늦은 정정·복원 대조에 쓸 이력이 줄어든다. 학습 기록과 동시 삭제하면 기간 중 잔여량을 잃을 수 있다. 두 기한 모두 운영 실측 전 제안값이며 유료/체험의 집계 기간 길이·갱신 정책은 별도 미정이다. |
| 학습 세션과의 관계 | **A 제안:** 사건 생성 시 소유자·기간·학습 세션 식별자를 기록하되 학습 세션 만료가 원장을 연쇄 삭제하지 않게 한다. 계정 탈퇴는 원장까지 삭제하고, 기한 경과한 학습 세션의 본문·노트는 원장에서 역참조하지 않는다. | 학습 세션 FK 삭제에 원장도 연쇄 삭제한다. | A는 기간 합계 보존에 필요하지만 원장 정리·탈퇴 범위와 소유자 검증이 늘어난다. 세션 ID·공급자 요청 ID는 본문이 아닌 식별 메타데이터로 제한하고 외부 로그에 복사하지 않는다. |
| 미확정 사용량 | **A 제안:** 실패·취소·응답 누락 사건을 즉시 0으로 확정하지 않고 예약 상태로 남겨 공급자 사용 기록과 대조한다. 측정 전에는 자동 해제 시간을 확정하지 않고 비공개 시험에서 상태·잔여량·지연을 관찰한다. | 응답 실패 시 즉시 예약을 전부 해제하거나 영구 예약한다. | 즉시 해제는 늦은 청구로 한도를 넘길 수 있고 영구 예약은 잔여량을 계속 묶는다. 자동 해제 기한·최대 예약량은 정상/취소/단절/재연결의 보고 지연과 청구 오차를 측정한 후 별도 결정한다. 이 항목의 A는 영구 집행 정책 승인이 아니며 자동 해제 없는 공개 운영을 뜻하지 않는다. |

위 A안 중 보존 기간과 학습 세션 관계는 사용자 데이터 수명에 영향을 주므로 승인 전에는 DB 스키마·마이그레이션·제품 계약에 반영하지 않는다. 승인 후에도 원장에 발화·전사문·음성·노트 본문·비밀값을 넣지 않고, 동일 요청/재시도/늦은 보고를 한 번만 정산하는 제약과 탈퇴 삭제를 검증한다. 미확정 예약의 자동 해제·허용 초과 오차·공개 직접 연결 경로는 실측 후 따로 결정한다.

A안 채택 시 DB 이관과 만료/탈퇴 작업·복원 검증이 추가돼 일정과 저장/운영비가 늘어난다. 기간 합계를 유지하면 무료 노트가 만료된 뒤에도 그 기간의 이용 가능 상태를 일관되게 보여줄 수 있다. 미확정 예약이 오래 남으면 사용자는 실제보다 적은 잔여량을 볼 수 있으므로, 공개 이용 전에는 해제 기준을 확정하고 실패/정정 안내를 검증해야 한다. 30일 보존안은 저장량을 줄이고, 학습 기록과 동시 삭제하는 안은 기간 집계의 신뢰성을 낮출 수 있다.

### 새 방향 검토: 시간·활동량과 주간 과금 대조

사용자는 요청별 토큰을 계속 계측·정산하는 대신 앱이 아는 사용자 수와 이용 시간으로 주간 실제 API 비용을 대조해 Talkie 자체 기준을 만들자고 제안했다. 아래 B안은 [DEC-062](../adr/062-TIME-BASED-VOICE-ALLOWANCE-AND-WEEKLY-COST-REVIEW.md)로 승인됐고 DEC-060/061의 토큰 집행을 대체한다. 위 토큰 원장 30/90일 보존 제안은 채택하지 않았다.

| 방향 | 동작과 장점 | 비용·일정·사용자 경험·데이터·운영 영향 |
| --- | --- | --- |
| A. 시간만 기록하고 주간 평균으로 사후 판단 | 계정 수·학습 세션 시작/종료·전체 연결 시간을 모아 주간 총비용 ÷ 총시간을 본다. 토큰 원장·예약 구현이 가장 적다. | 주중 과다 사용을 막기 어렵고, Live/분리형 경로·모델·노트 호출이 섞이면 평균이 달라진 원인을 알기 어렵다. 긴 단일 연결·동시 접속과 무료 등급 비용 0의 표본은 유료 운영비를 대표하지 않는다. |
| **B. 시간 기반 이용권 + 최소 운영 계측(채택)** | 서버가 계정/기간별 허용 연결 시간을 부여하고 새 연결을 열 때 잔여 시간·동시 연결·연결당 상한을 검사한다. 토큰 수는 저장·정산하지 않는다. 사용자에게는 사용 가능 시간/마무리 상태를 안내하고, 별도 노트 호출 횟수·실패를 제한한다. 주간 공급자 실제 과금 총액과 연결 시간·문답 수·노트 건수를 대조하고, 기능별 금액은 귀속 근거가 있는 범위만 실제액으로 써 기준을 보정한다. | 토큰 원장보다 구현 범위가 작지만 시간 승인·재접속·중복 발급의 지속 상태와 시간 만료 시 마무리 경험은 필요하다. 같은 시간의 비용은 문답 수·Live 누적 맥락·출력 길이에 따라 달라져 주간 평균은 예측값이지 개별 사용자 비용 보장이 아니다. 공급자 측 계정/프로젝트 지출 한도·알림과 앱의 발급/동시성 제한을 함께 검증해야 한다. |
| C. 이전 결정 유지 | 종류별 토큰 사용량·원자적 예약/정산으로 세션/기간 한도를 집행한다. | 비용 차이를 더 직접 반영하지만 서버/직접 연결 계측·원장·지연 보고·오차 검증에 가장 많은 구현/운영 부담이 든다. DEC-060/061의 과거 계약이다. |

B안의 ‘시간’은 학습 세션이 열린 뒤의 경과 시간이 아니라 **공급자 연결을 허용한 시간**으로 정의하는 것이 후보이다. 앱에 있는 `learning_session_started_at`/종료 시각만으로는 실제 WebSocket 연결·중단·재접속 시간을 확정할 수 없다. 서버가 발급한 단일 사용 연결 권한의 시작·최대 지속시간을 누적하면 실제 사용보다 다소 크게 잡히더라도 상한을 관리할 수 있다. Gemini 임시 토큰의 `expireTime`은 이후 메시지 거절 시점이고 [Soniox 임시 키의 `max_session_duration_seconds`](https://soniox.com/docs/guides/temporary-api-keys)는 스트림 상한이다. 브라우저가 보낸 종료 시각만으로 잔여량을 환급하면 조작·누락 위험이 있어 실제 해제·환급 기준은 검증 후 정한다. 기존 3분 로컬 시험값은 제품 시간 상한이 아니다.

주간 대조는 [Google Cloud Billing 보고](https://docs.cloud.google.com/billing/docs/how-to/reports)의 Gemini API 서비스/SKU 비용과 [Soniox 사용 기록·일일 요약](https://soniox.com/docs/guides/usage-logs)의 금액을 사용한다. Google의 청구 단위가 앱 기능/요청과 일치한다고 가정하지 않는다. 같은 모델/SKU를 대화와 노트가 공유하면 총액을 기능별 실제액으로 분리할 근거가 없으므로 그 부분은 추정·미확인으로 표시한다. [Gemini Live 과금 안내](https://ai.google.dev/gemini-api/docs/live-api/best-practices)에 따르면 연결 중 입력 음성 및 턴마다 재처리되는 누적 맥락, 전사 텍스트와 출력 종류가 비용을 바꾸므로 `총비용 ÷ 전체 연결 시간` 한 값만으로 두 경로를 함께 예측할 수 없다. Cloud Billing 상세는 보통 하루 안에 표시되지만 더 늦을 수 있어 주간 집계의 확정 시점과 수정 규칙이 필요하다. 실제 유료 표본·귀속 가능한 경로별 비용이 없으면 시간당 기준을 확정하지 않는다.

채택된 B안의 현행 제품 계약은 PRD 6·9.2절, 구현 경계는 음성 설계를 따른다. 계정당/기간별 시간 수치, 연결당 상한, 주간 비용의 허용 편차·대응, 데이터 보존 기한과 공개 운영 공급자 지출 한도는 후속이다. 이 비교는 구현 완료나 유료 운영비의 실측 근거가 아니다.

### 다음 결정 검토: 시간 이용권의 발급·소진 경계

DEC-062의 연결 허용 시간은 승인됐지만 실제 연결을 서버가 독립 관측하지 못하는 Live·Soniox 직접 연결에서는 발급 시점과 사용 종료 시점이 다르다. 현재 `voice-token.ts`의 180초 단일 프로세스 시험 제한은 재시작과 동시 기기에서 유지되지 않으며 제품 이용권 수치도 아니다. 아래 1~3·5번은 [DEC-063](../adr/063-OBSERVED-VOICE-TIME-AND-ACCOUNT-ALLOWANCE-STATE.md)으로 승인됐다. 4번은 사용자가 **우선 A안**을 택한 잠정 방향으로, 마무리 안내 후 한도에서 종료하고 미완료 교정·재시도를 성공으로 보지 않는다. 유예 시간·기간·분 수치, 직접 연결의 독립 검증과 공개 공급자 경로는 별도 결정한다.

| 선택 | 추천안 | 대안과 영향 |
| --- | --- | --- |
| 1. 차감 단위와 시점 | **합의한 방향:** 웹 브라우저가 공급자 연결이 열린 시각부터 닫힌 시각까지의 시간과 대화 수를 관찰·보고한다. 서버는 연결 중 신호를 받은 서버 시각과 대조해 관찰된 연결 시간을 이용권에서 누적 차감한다. 발급 전 잔여 시간·연결당 최대 시간을 확인하되 최대 허용 시간 전체를 사용량으로 즉시 차감하지 않는다. | 기존 발급 시 최대 시간 전체 차감안은 짧은 이용·미사용 발급에 불리해 채택하지 않았다. 브라우저 보고만 믿으면 누락·조작과 동시 기기 우회가 가능하므로 서버 수신 기록·공급자 상한을 함께 검증한다. 종료 신호가 없는 구간의 차감은 2번에서 정한다. |
| 2. 미사용·연결 끊김 시간 | **A 선택:** 연결 중 서버가 마지막으로 확인한 시각부터 짧은 유예 기간까지만 사용한 것으로 계산하고, 이후에는 연결이 끊긴 것으로 처리한다. 연결이 실제 열리지 않은 발급은 차감하지 않는다. 종료 보고가 늦거나 없는 경우의 유예 길이와 공급자 사후 기록 대조는 검증 후 정한다. | **B 미채택:** 브라우저가 보고한 종료 시각만으로 즉시 차감을 멈춘다. B는 짧은 이용을 정확히 반영할 수 있지만 보고 누락·조작과 공급자 연결 잔존을 서버가 확인하지 못한다. A는 단절 뒤 일부 시간을 더 차감할 수 있어 유예 길이·안내·정정 기준이 필요하다. |
| 3. 동시 연결·재시도 | **A 선택:** 계정의 활성 발급은 경로와 기기를 합쳐 하나로 제한한다. 동일 요청 ID의 재전송에는 새 권한을 발급하지 않는다. 연결 종료가 독립 확인되지 않으면 공급자 최대 지속시간 안에서 재발급을 보수적으로 제한하고, 해제 조건·오류 안내를 검증해 정한다. | **B 미채택:** 경로별 별도 활성 발급을 허용한다. B는 기기 전환에 편하지만 여러 공급자 연결과 기간 잔여 시간 경쟁을 늘린다. A는 일시 연결 오류 시 재시작 지연이 생길 수 있어 남은 대기 시간을 보여줘야 한다. 학습 대화 하나 제약(DEC-032)과 별개로 발급 상태를 검증한다. |
| 4. 시간 경계의 대화 경험 | **A 우선 선택:** 새 연결 전 잔여량을 알리고 연결 중 종료가 가까워지면 새 소재 질문을 중단해 마무리를 알린다. 공급자 상한 도달 때 음성을 닫고 확인된 발화·재생 근거만 저장한 뒤 별도 노트 정리로 넘어간다. 교정/재시도가 진행 중이면 미완료 상태로 남기며 성공으로 간주하지 않는다. | **B 보류:** 현재 교정/재시도가 끝날 때까지 연결을 연장한다. B는 학습 흐름이 자연스럽지만 공급자 상한을 넘거나 별도 예약이 필요하다. A는 끊긴 느낌을 줄 수 있어 안내 시점·문구·경계 1턴의 합성 시험이 필요하다. 24시간 재개는 기록 처리 기한이며 소진된 음성 시간을 새로 주지 않는다. |
| 5. 최소 이용 상태의 수명 | **A 선택:** 계정의 이용 기간·허용/사용 시간과 활성 연결 판단 상태를 학습 기록과 독립적인 별도 이용권 테이블에 지속 저장하고 탈퇴 때 함께 삭제한다. 기간별 상태를 구분하며 연결 발급 이력·주간 대조 자료의 세부 배치와 수명은 후속으로 정한다. | **B 미채택:** `users` 열만 늘리면 첫 구현은 단순하지만 기간 전환과 이력 관리가 계정 식별 행에 쌓인다. 학습 세션 행에 넣으면 학습 원문·노트 만료와 이용권 갱신 시점이 달라 잔여량을 잃을 수 있다. A도 새 테이블·마이그레이션·정리와 백업 복원 후 이중 차감 방지 검증이 필요하다. |

1~3·5번의 합의는 차감·동시성·저장 경계이며 직접 연결의 서버 독립 계측이 확인됐다는 뜻은 아니다. 발급 권한이 공급자 연결을 해당 최대 시간에 확실히 끝내지 못하면 비용 상한을 주장할 수 없고, 그 경로의 중계·비공개 유지·경로 제외를 다시 비교해야 한다. 종료 보고 누락과 동시 발급의 경계를 검증하고 실제 유료 과금과 대조한 뒤 기간/분 수치를 정한다. 새 공급자 호출이나 공개 연결은 이 검토만으로 승인되지 않는다.

## 남은 검증과 영향

DEC-062의 현행 방향은 사용자에게 금액을 청구하는 지갑 기능 없이 연결 허용 시간과 별도 노트 호출 제한으로 이용을 관리하고 경로별 주간 실제 과금으로 조정하는 것이다. Live 직접 연결과 분리형 STT 연결에서 서버 발급 권한·공급자 상한으로 시간을 집행할 수 있는지 확인해야 한다. 불가능하면 해당 경로의 중계 등 변경을 논의한다. 최종 공급자 적합성·유료 호출/공개 연결 승인은 과거 토큰 계산으로 확대하지 않는다.

두 경로의 실제 대화에서 연결 허용 시간·문답 수·노트 호출과 경로별 실제 주간 과금, 단절·재연결·무음·마무리의 편차를 확인해야 한다. 시간 한도의 우회·이중 차감과 공급자 지출 상한의 효과도 검증 대상이다. 기존 Live 계산은 공식 자료와 산정 가정에 따른 것이며 유료 운영비나 시간당 보장 비용이 아니다.
