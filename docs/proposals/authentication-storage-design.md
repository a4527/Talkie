# 인증·저장 상세 설계 초안

작성일: 2026-10-23. 상태: 1A·3A·4A·5A 채택(DEC-041~044), 2B는 Drizzle ORM으로 채택(DEC-045). 후속 사용자 정책은 DEC-046/047로 채택했고 구체 구현 계약은 검토 중이며 설치·구현·검증을 뜻하지 않는다.

기준은 [PRD 8절](../../PRD.md#8-저장-데이터와-학습-노트), [현재 설계](../../design.md), [결정 목록](../../DECISIONS.md)과 [최소 MVP 점검표](minimum-mvp-decision-checklist.md)의 L02~L20이다. D-02를 먼저 구체화하고 B-01/B-05에 연결한다. 기존 이메일 링크·보관·삭제·DB 분리 정책은 다시 선택하지 않는다. 합의 전에는 이 문서의 후보를 현재 설계나 Accepted 결정으로 옮기지 않는다.

## 먼저 논의할 다섯 선택

현재 합의: 사용자가 “그래 drizzle orm으로 해보자”라고 동의해 2B를 Drizzle ORM·Drizzle Kit으로 구체화했다([DEC-045](../../DECISIONS.md#dec-045)). 다섯 기술 선택은 모두 확정됐으며 아래 표의 A 추천은 최초 제안 당시 상태다. 초기에는 SQL 제어·관찰을 중시해 2A를 추천했지만, 사용자가 두 방식 모두 경험이 적다고 설명한 뒤 타입·스키마/마이그레이션 도구 지원과 직접 SQL을 함께 쓸 수 있는 Drizzle을 추천했다. 반복 코드 부담을 줄일 것으로 판단하되 실제 개발 일정·성능 우위를 측정한 것은 아니다. 학습할 도구와 의존성이 추가되며 인증·두 저장소 정합성은 직접 검증해야 한다. DB 분리·사용자 동작·보관/삭제·외부 전송 경계는 유지한다.

후속 합의: 사용자가 “나머지는 다 A로 하고 2번은 무슨차이야?”라고 명시했다. 1A·3A·4A·5A는 [DEC-041~044](../../DECISIONS.md#dec-041)와 [현재 구성](../../design.md#로컬-인증저장-검증-구성)에 반영했다. 2번 질문은 동의로 해석하지 않는다. 아래 추천·동의 전 표현은 최초 제안 당시 설명이며 데이터 모델·프로토콜 전체를 승인한 것은 아니다.

인증·저장 통합에 필요한 로컬 실행과 검증 범위를 먼저 정한다. 번호는 이번 논의용이며 DEC ID가 아니다. 사용자 경험·운영 영향이 있는 기술을 포함하므로 명시적 동의 후 채택한다.

| 번호·연결 | A · 추천 | B · 대안 | 이유와 비용·일정·사용자·데이터·운영 영향 |
| --- | --- | --- | --- |
| 1 · L06/L07 DB 실행 | Docker Compose로 PostgreSQL 두 인스턴스와 분리 볼륨 실행 | 호스트에 PostgreSQL을 설치하고 두 클러스터 직접 관리 | A는 재현·시험 초기화 설정을 파일로 관리하기 쉽지만 Docker 설치·데몬·볼륨 관리가 추가된다. B는 Docker 없이 실행하나 버전·포트·서비스 설정을 호스트에서 관리한다. 두 안 모두 로컬 자원 사용과 백업 제외 검증이 필요하며 성능 우열은 미측정이다. 클라우드 비용·배포는 포함하지 않는다. |
| 2 · L06 DB 접근 | node-postgres(`pg`)와 버전 관리 SQL 마이그레이션 | ORM과 해당 마이그레이션 도구 | A는 잠금·조건부 제약·트랜잭션을 SQL로 직접 확인하기 쉽다. 대신 조회 결과의 런타임 검증·타입·마이그레이션 실행/검증을 직접 관리한다. B는 모델/타입 생성에 유리할 수 있으나 도구 학습·생성물과 원시 SQL을 함께 관리할 수 있다. 선택만으로 성능·보안·개발 일정 우위를 보장하지 않는다. 기존 계정별 접근 정책은 동일하다. |
| 3 · L02 인증 메일 시험 | 로컬 Mailpit으로 합성 주소의 메일 수신·확인부터 검증하고 실제 전달 서비스는 별도 선택 | 실제 메일 서비스 선정·발신자 설정부터 진행 | A는 외부 수신자·메일 서비스 계정 없이 링크 흐름을 시험한다. 실제 받은편지함·스팸·지연/반송 적합성은 미검증으로 남는다. B는 실제 전달을 일찍 확인하지만 도메인·외부 계정·비용·이메일/인증 링크 처리 경계를 먼저 정해야 한다. A의 메일함도 비밀 링크를 담으므로 로컬 한정·시험 종료 시 폐기하며 로그나 백업으로 복사하지 않는다. |
| 4 · L16 로컬 기한 작업 | 웹 서버와 분리된 명령을 Linux 사용자 systemd timer로 정시 실행 | 호스트 cron으로 같은 명령 실행 | A는 실행 상태·실패를 서비스 단위로 확인하고 재실행을 관리한다. 사용자 서비스 수명·로그아웃·절전·재부팅과 실제 timer 지원을 확인해야 한다. B는 단순하지만 실행 누락·중복·출력/실패 관리를 별도로 구성한다. 둘 다 꺼진 컴퓨터에서 기한 준수를 보장하지 않는다. 로그인 없이 상시 실행하기 위한 호스트 설정 변경은 별도 확인하며 운영 플랫폼은 미채택이다. |
| 5 · L19 백업 검증 착수 범위 | 합성 데이터로 지속 DB 백업·복원·삭제 상태 재적용 시험부터 구현하고 시험 사본은 종료 시 폐기 | 처음부터 주기적 로컬 백업·보관/폐기까지 함께 설계·구현 | A는 임시 원문 제외와 복원 차단을 작은 범위로 먼저 검증한다. 실제 사용자 데이터 보관 전에는 생성 주기·자동 폐기·보호·복구 목표를 추가 확정해야 한다. B는 자동 보관 경로를 빨리 다루지만 비밀값/개인정보 사본·키 관리·탈퇴 7일 상한·체험 만료를 함께 해결해야 하므로 초기 범위가 커진다. A는 실제 계정 데이터의 무백업 운영을 승인하는 선택이 아니다. |

추천은 `1A 2A 3A 4A 5A`. 의도는 로컬 합성 데이터로 인증과 두 저장소의 경계를 먼저 검증하는 것이다. 무료 운영이나 실제 메일 전달·운영 기한 준수의 보장은 아니다. 현재 셸 PATH에서 `docker`·`psql`은 발견되지 않았고 `systemctl`은 발견됐다. Docker 데몬·사용자 systemd 세션·DB 실행 가능성은 미검증이며 설치나 서비스 등록은 수행하지 않았다.

## 인증 데이터 모델 제안

다음은 기존 직접 인증·지속 PostgreSQL 방향을 구체화한 논리 모델이다. SQL 스키마·이름·인덱스·마이그레이션은 아직 적용하지 않았다. 비밀 토큰은 충분한 난수로 생성하고 DB에는 검증용 해시만 둔다. 이메일과 내부 사용자 ID도 민감 데이터로 취급하며 진단 로그에서는 제외한다.

| 대상 | 최소 필드·관계 | 제약과 수명 |
| --- | --- | --- |
| 사용자 | 내부 ID, 이메일 식별값, 계정 상태, 가입 시각, 탈퇴 확정 시각 | 이메일 식별 규칙은 아래 미정 목록을 따른다. 탈퇴 대기 계정은 접근 불가. 확인되지 않은 메일 요청만으로 정식 사용자나 체험 이력을 만들지 않는다. |
| 이메일 인증 요청 | 요청 ID, 대상 이메일/사용자, 목적, 세대 번호, 토큰 해시, 발급/만료/사용/무효화 시각, 전달 상태 | 로그인·탈퇴 재확인 목적을 분리한다. 발급 후 10분, 목적별 최신만 유효, 조건부 갱신으로 한 번만 소비한다. 토큰 원문·메일 본문은 저장하지 않는다. |
| 메일 요청 제어 | 이메일 식별값, 마지막 요청 시각, 목적별 최신 세대 | 동시 요청에서도 같은 이메일의 30초 간격을 지킨다. 첫 요청으로 행이 아직 없는 경우도 고유 제약과 잠금/충돌 재시도로 직렬화한다. 횟수 상한은 추가하지 않는다. |
| 로그인 세션 | 내부 세션 ID, 사용자 ID, 쿠키 토큰 해시, 생성/마지막 이용/만료/무효화 시각 | 인증 성공 시 생성. 유효하고 계정이 활성인 세션만 이용 시 30일로 갱신한다. 만료·로그아웃·탈퇴로 무효화된 세션은 갱신 불가. 학습 대화 ID와 분리한다. |
| 탈퇴 확인 권한 | 사용자 ID, 로그인 세션 ID, 확인 시각, 만료/소비 시각 | 이메일 재확인 성공 후 해당 브라우저의 로그인 세션에만 연결한다. 10분 내 최종 확정에 한 번 사용하고 로그아웃·탈퇴 후 재사용하지 않는다. |

토큰 길이·해시 방식은 design의 인증 구현 상세, 인증용 행 정리 기한은 DEC-046을 따른다. 메일주소 정규화·정리 작업/경계 구현은 남는다. 메일주소 전체를 임의 소문자화하거나 서비스별 점/별칭을 제거해 서로 다른 주소를 자동 병합하지 않는다. 만료 행의 사용 차단과 실제 행 삭제를 구분한다.

## 인증 흐름과 동시성

1. **링크 요청:** 이메일·허용된 목적을 검증하고 서버에서 대상과 발송 간격을 확인한다. 동일 이메일 요청을 직렬화하여 새 세대 발급과 이전 미사용 링크 무효화를 한 트랜잭션에서 처리한다. 외부 입력으로 링크의 호스트·리다이렉트 목적지를 정하지 않는다.
2. **메일 전달:** DB 트랜잭션과 SMTP 전달은 하나의 원자적 작업이 아니다. 전달 성공/실패/불명을 구분한다. 토큰 원문을 지속 작업 목록에 넣어 재전송하지 않는다. DEC-046에 따라 자동 재발송과 실패 전용 재요청 안내/버튼을 추가하지 않고 기존 요청 화면에서 다시 요청할 수 있다. 30초 간격·새 링크의 이전 미사용 링크 무효화를 유지한다.
3. **링크 열기:** GET/미리보기는 사용 처리·가입·로그인·탈퇴를 일으키지 않는다. 외부 리소스 없는 확인 화면을 제공하고 링크 토큰이 Referer·접근 로그·오류 본문에 남지 않도록 한다. 토큰의 URL 운반 방식·중간 확인 쿠키·주소 표시 정리 방법은 구현 전에 명세한다.
4. **사용자 확인:** 서버가 보호된 확인 요청에서 목적·최신 세대·미사용·만료를 다시 검증한다. 한 트랜잭션에서 토큰 소비와 사용자 생성/조회 및 로그인 세션 생성을 처리한다. 로그인 세션 토큰 원문은 브라우저 쿠키로만 전달한다. 동시에 확인해도 성공은 한 번이다. 탈퇴 재확인은 별도 목적과 기존 세션 연결을 검증한다.
5. **인증된 요청:** 서버에서 세션·계정 상태와 대상 데이터 소유자를 검증한다. 브라우저가 보낸 사용자 ID를 권한 근거로 쓰지 않는다. DB 장애를 인증 성공으로 처리하지 않으며 단순 갱신 경쟁이 로그아웃/탈퇴 상태를 되살리지 못하게 한다.
6. **쿠키와 요청 보호:** HttpOnly·SameSite·Path·만료 및 HTTPS의 Secure 속성을 명세한다. 로컬 HTTP 예외를 원격 환경에 허용하지 않는다. 변경 요청에는 Origin 검증과 CSRF 보호를 적용하고 캐시에서 인증/기록 응답이 공유되지 않게 한다.
7. **탈퇴 확정:** 계정 상태 변경·전체 로그인 세션 무효화·삭제 작업 등록을 지속 DB의 한 트랜잭션에서 처리한다. 진행 작업의 지속 결과 저장도 같은 계정 상태를 확인하고 탈퇴와 직렬화한다. 임시 DB의 지연 쓰기는 별도 방어가 필요하며 아래 경계를 따른다.

로그인할 브라우저는 DEC-046으로 확정했다. 로그인 확인 성공 후 응답/쿠키 전달이 유실됐을 때의 상세 복구 계약은 아직 명세되지 않았다. 탈퇴 확인 권한의 브라우저 귀속은 기존 정책을 유지한다. 장기 음성 연결의 즉시 무효화는 HTTP 요청마다 인증하는 것만으로 달성되지 않으므로 연결 제어 계약과 공급자 시험을 별도로 둔다.

## 학습 저장 모델과 두 DB의 경계

| 위치 | 논리 대상 | 원문과의 경계 |
| --- | --- | --- |
| 지속 PostgreSQL | 사용자·인증 상태·이용 권한, 학습 세션 메타데이터, 저장 확정 위치, 최초 중단/종료 시각, 삭제/노트 작업, 요약·선별 학습 항목·짧은 근거·날짜별 노트 | 전체 발화·전체 진행 상태를 JSON이나 작업 payload로 우회 복사하지 않는다. 이력/교정의 지속 범위는 선별된 항목과 필요한 근거에 한정한다. |
| 임시 PostgreSQL | 확인된 턴·전달/재생 범위·교정/재시도 이벤트·대응 진행 상태, 저장 묶음 ID/순서/버전, 최초 만료 기한 | 전체 전사문과 원문을 포함할 수 있는 진행 상태는 임시 저장에 함께 둔다. 두 DB 사이 외래 키나 단일 트랜잭션을 가정하지 않는다. |

계정당 진행 대화 하나는 중단 상태도 포함하는 조건부 고유 제약으로 보호하는 안을 둔다. 계정과 학습 세션의 ID를 임시 저장에서도 연결하되 인증 비밀값은 복사하지 않는다. 노트는 세션별 선별 결과와 종료일로부터 날짜별 보기를 구성하여 같은 날 동시 완료가 기존 결과를 덮지 않게 한다. 물리적 노트 집계 방식은 아직 미정이다.

저장 프로토콜 제안은 다음과 같다.

- 요청마다 계정·세션 소유자와 접근 가능 상태를 검증하고, 묶음 ID·순서·내용 검증값으로 재전송과 충돌을 구분한다. 같은 ID에 다른 내용을 보내면 성공으로 처리하지 않는다.
- 임시 DB에서 턴과 대응 상태를 함께 커밋한 뒤 지속 DB의 확정 위치를 갱신한다. 두 단계가 확인돼야 앱에 저장 성공을 알린다. 중간 실패·응답 유실은 같은 ID로 재확인한다.
- 임시 DB에만 저장된 묶음은 확정 위치를 넘어 복원·노트 생성에 사용하지 않는다. 지속 DB의 위치만으로 임시 데이터가 실제 존재한다고 단정하지 않는다. 복원 후 원문이 없는 세션을 만들어 채우지 않는다.
- 탈퇴·종료·만료 경쟁은 단순 사전 조회만으로 막히지 않는다. 임시 쓰기 직렬화, 삭제 차단 표식과 세대 검증, 지속 작업의 재조정 절차를 구현 전 구체화해야 한다. 삭제 후 늦은 쓰기가 원문을 재생성하는 경우까지 시험한다. 이 초안의 두 단계만으로 해결됐다고 보지 않는다.
- 노트와 검증된 근거를 지속 DB에 커밋한 후 임시 원문 삭제를 실행한다. 삭제 실패 시 결과를 덮어 만들지 않고 삭제를 재시도한다. 최초 종료 후 24시간 상한은 변하지 않는다.

추천 답변은 이번 묶음 기준 `1A 2A 3A 4A 5A`다. 3번의 삭제 수치는 로컬 기기가 실행 중인 조건으로 검증하고 꺼진 동안 기한 준수를 보장하지 않는다. 5번 버퍼의 바이트/항목 상한·너무 큰 단일 단위의 처리·구간별 순서/재개 상태는 합의한 방향 안에서 구현 전 명세하고 부하/장애 시험으로 검증한다. 초과 시 디스크/브라우저 저장소에 원문을 우회 저장하는 안은 포함하지 않는다. 로컬 합성 시험부터 적용하며 실제 사용자·공급자 연결 승인이 아니다.

### 구현 상세의 구체화 범위

토큰 난수 32바이트·base64url·SHA-256 검증값·UTC 만료 판정은 [현재 인증 구현 상세](../../design.md#인증-구현-상세)에 정리했다. 이는 기존 비밀값 보호·일회성/최신 링크·30초/10분/30일 계약 안의 구현 선택이며 새 사용자 정책 채택이 아니다. 다음 물리 모델은 세부 컬럼을 작성하기 위한 검토 구조다.

| DB | 테이블 후보 | 핵심 제약 |
| --- | --- | --- |
| 지속 | users, auth_request_controls, auth_challenges, auth_sessions, deletion_confirmations | 이메일 식별값 고유성, 목적/세대·토큰 해시 고유성, 사용자 연결, 만료/무효화 조건. 미인증 요청으로 사용자/체험 시작을 만들지 않음 |
| 지속 | learning_sessions, save_receipts, scheduled_jobs | 계정당 active/interrupted 대화 하나, 세션/묶음 ID 고유성, 동일 ID 다른 내용 거부, 종료 최초 시각·확정 위치·작업 최초 기한 |
| 지속 | session_notes, learning_items, evidence_fragments | 사용자/세션/노트 버전 연결, 검증된 짧은 근거만 보관, 같은 날짜 결과의 갱신 충돌 방지 |
| 임시 | transcript_sessions, transcript_batches, confirmed_events | 임시 세션 접근 상태·세대·최초 삭제 기한, 묶음 순서/내용 검증, 턴과 대응 진행 상태의 원자 저장 |

턴·재생/교정/재시도 이벤트·버전 형식은 실제 음성 공급자 계약 확정 전 텍스트 프로토타입 형식으로 고정하지 않는다. 이메일 식별 규칙, 물리 인덱스와 삭제/복원용 보조 데이터 수명은 여전히 명세 대상이다.

두 저장소의 실패 분석을 아래처럼 확장했다. 이는 검토할 알고리즘이며 검증 완료나 새로운 저장 아키텍처 채택이 아니다.

| 실패/경쟁 | 반드시 지킬 결과 | 설계/시험할 처리 |
| --- | --- | --- |
| 임시 커밋 전 실패 | 저장 성공 표시 없음 | 같은 묶음 ID 재시도, 턴/상태 부분 반영 없음 |
| 임시 커밋 후 지속 확정 전 실패 | 미확정 묶음을 재개/노트 근거로 사용하지 않음 | 임시 저장의 같은 ID/내용 확인 후 지속 확정 재시도. 고립된 묶음도 최초 기한에 정리 |
| 양쪽 커밋 후 응답 유실 | 재전송이 중복 턴/상태를 만들지 않음 | 지속 receipt와 임시 묶음의 ID/내용·기한을 재확인. 지워진 원문은 receipt로 재생성하지 않음 |
| 탈퇴/노트 완료/원문 만료와 지연 쓰기 경쟁 | 접근 차단 뒤 새 저장 성공 없음, 삭제 후 원문 부활 없음 | 지속 계정→학습 세션→임시 세션의 일정한 잠금 순서와 조건부 쓰기를 검토. 임시 저장 경로는 기존 활성 세션 행을 요구하고 삭제 뒤 upsert로 재생성하지 않음 |
| 지속 연결 손실로 잠금이 먼저 풀리고 임시 쓰기가 남음 | 잠금만으로 양 DB 원자성이 있다고 주장하지 않음 | 임시 DB의 접근 차단/세대·기한과 삭제 작업 직렬화, 지연 트랜잭션/연결 종료 주입 시험. 논리 확정 차단과 물리 임시 쓰기 잔존을 각각 측정하고 구현 전 프로토콜 확정 |
| 지속 백업 복원 후 임시 원문 없음 | 존재하지 않는 원문·근거를 꾸며 복원하지 않음 | 원문 없는 상태로 표시하고 저장된 노트/근거만 제공. 미완성 작업의 처리·삭제 상태 재적용 뒤 개방 |

두 저장소 경계를 해결하지 않은 상태로 원문 저장 기능을 완료 표시하지 않는다. 이 설계가 실패하면 기존 분리/백업 제외 정책 안의 대안을 먼저 비교하고, 데이터 경계나 채택된 결정을 바꾸는 대안은 사용자와 다시 논의한다.

후속 다섯 정책은 DEC-046/047로 채택했다. 남은 상세는 버퍼 상한 수치/큰 단위·유실 구간의 저장/재개 정합성, 실제 메일 서비스와 전달 상태 판정, 이메일 식별/쿠키/링크 운반, 기한 작업 실행/재시도 수치, 체험 만료의 백업 처리·삭제 상태 재적용과 두 DB 경쟁 프로토콜이다. 버퍼 유실은 명시하며 대화 정지나 조용한 폐기는 허용하지 않는다.

구현 순서는 로컬 두 DB/메일 시험 환경 → 마이그레이션/합성 데이터 → 링크·세션 인증과 타 계정 접근 차단 → 저장 중복/부분 실패·기한 작업 → 백업/복원·삭제 경쟁 검증으로 제안한다. 실제 사용자 데이터 보관 전 D-02와 B-01 접근 통제 검증, 실제 메일 전 외부 전달 경계 합의를 완료한다. 실제 AI가 필요한 학습·노트 통합은 D-03/B-09 선행 관계를 유지한다.

필수 검증에는 링크 동시 소비·재발급/소비 경쟁·30초/10분/30일 경계, 미리보기 미소비, DB 오류 시 접근 차단, 로그아웃/탈퇴와 갱신/저장 경쟁, 다른 계정 기록 차단, 두 DB 중 한 곳만 커밋·응답 유실·백업 복원 후 원문 부재·삭제 상태 재적용을 포함한다. 아직 SQL 실행·보안 테스트·복원 시험·성능 측정은 하지 않았다. D-02/B-01/B-05 상태는 유지한다.

## 외부 근거와 한계

2026-10-23 공식 문서를 확인했다. 아래는 기능 관찰이며 Talkie의 안전성·성능·비용 실측 결과가 아니다.

- [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): 세션 식별자 보호·쿠키 속성·서버 측 무효화 근거. Talkie의 30일 수명은 기존 사용자 결정이다.
- [OWASP 일회성 링크 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html): 무작위·일회성·기한·노출 방지와 계정 존재 노출 방지의 참고다. 비밀번호 재설정 지침을 이메일 로그인에 적용하는 것은 설계 판단이며 완성된 로그인 프로토콜의 증거가 아니다.
- [PostgreSQL 잠금](https://www.postgresql.org/docs/current/explicit-locking.html): 같은 DB 내 동시 변경의 직렬화 수단. 두 인스턴스의 원자성을 제공한다는 근거는 아니다.
- [PostgreSQL 격리 수준](https://www.postgresql.org/docs/current/transaction-iso.html)·[Node.js crypto](https://nodejs.org/api/crypto.html): 동시성/재시도 조건과 난수·해시 API의 기능 근거다. 32바이트 난수·SHA-256 조합은 Talkie 구현 선택이며 API 존재만으로 인증 프로토콜의 안전성이 검증된 것은 아니다.
- [node-postgres 트랜잭션](https://node-postgres.com/features/transactions): 한 트랜잭션에 같은 client를 사용해야 하며 pool의 개별 query를 섞지 않는다. A의 직접 SQL/검증 부담을 전제로 한다.
- [Drizzle PostgreSQL 연결](https://orm.drizzle.team/docs/get-started-postgresql)·[마이그레이션](https://orm.drizzle.team/docs/migrations)·[SQL 지원](https://orm.drizzle.team/docs/sql): PostgreSQL 드라이버 연결·SQL 마이그레이션 생성/적용·매개변수화 SQL을 지원한다. 공식 안내의 RC 설치 예시는 이번 채택에서 버전 선택으로 확장하지 않는다. 설치 때 안정 버전·호환성을 확인하며 ORM 타입을 런타임 검증으로 간주하지 않는다.
- [Docker Compose](https://docs.docker.com/compose/)·[볼륨](https://docs.docker.com/reference/compose-file/volumes): 서비스/볼륨 구성을 파일로 관리한다. 호스트 스냅샷에서 자동 제외된다는 보장은 없다.
- [Mailpit Docker](https://mailpit.axllent.org/docs/install/docker/)·[실행 옵션](https://mailpit.axllent.org/docs/configuration/runtime-options/): SMTP 수신/UI와 저장 설정을 제공한다. 기본 임시 파일도 디스크 저장일 수 있으므로 채택 시 메일 저장은 메모리 기반 구성으로 검증하고 영속 볼륨·전달/릴레이·원문 로그를 사용하지 않는 시험 설정을 작성한다. 실제 전달 서비스로 간주하지 않는다.
- [systemd timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html): 예약 service 실행과 누락 보완 설정을 제공한다. 기기 종료 중 실행이나 정확한 시각 완료를 보장하지 않는다.
- [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html): 단일 DB의 일관된 내보내기를 지원한다. 사본 보호·자동 폐기·삭제 상태 재적용은 앱과 시험 절차의 책임이며 운영 백업 전략의 검증을 대체하지 않는다.
