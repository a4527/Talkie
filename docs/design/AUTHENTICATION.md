# 인증 설계

갱신일: 2026-10-28. 현재 구현은 루프백 환경과 합성 `.test` 이메일의 링크 인증이다. 로그인 유지·링크/탈퇴 기한·발송 정책은 [PRD 8.1](../PRD.md#81-가입로그인과-로그인-유지), 앱 직접 인증의 채택 근거는 [ADR-026](../adr/026-APP-MANAGED-EMAIL-LINK-AUTHENTICATION.md)을 따른다.

구현: [auth.ts](../../app/src/server/auth.ts), [HTTP·쿠키](../../app/src/server/http.ts), [이메일 입력 제한](../../app/src/server/config.ts), [확인 화면](../../app/src/app/account/confirm/page.tsx). HTTP 요청·응답은 [API](API.md#계정-api), 물리 테이블은 [DATABASE](DATABASE.md)를 따른다.

## 비밀값과 세션 경계

로그인 세션 ID와 학습 세션 ID는 분리한다. 링크·쿠키 비밀값은 각각 독립적인 32바이트 암호학적 난수를 base64url로 표현하고 DB에는 SHA-256 검증값만 저장한다. 사람이 고른 저엔트로피 비밀번호에 이 방식을 적용하지 않는다. 비밀 토큰 원문·메일 본문·인증 URL은 DB·지속 작업 payload·로그에 남기지 않는다.

브라우저의 `talkie_session` 쿠키는 HttpOnly·SameSite=Lax·Path=/와 로그인 수명에 맞는 maxAge를 사용한다. Secure는 현재 로컬 origin의 HTTPS 여부에 따른다. 루프백 HTTP 시험 예외를 운영 HTTPS 구성으로 해석하지 않는다. 연결 환경변수·쿠키 이름은 명명 정리로 바꾸지 않았다.

## 이메일 링크와 세션 처리

1. 주소의 앞뒤 공백과 도메인 대소문자를 정리하고 합성 `.test` 주소만 허용한다. 로컬 부분을 임의 소문자화하거나 점/별칭을 제거하지 않는다.
2. 같은 이메일 요청은 DB advisory transaction lock으로 직렬화한다. 제어 행이 아직 없는 첫 요청도 같은 잠금을 사용한다. 목적은 `login`·`account_deletion`으로 분리하고 발급 간격은 이메일 단위로 공유한다. 새 요청은 같은 목적의 미사용 링크를 무효화한다. 현행 구현은 별도 세대 번호 열 대신 무효화 상태로 최신 링크를 판별한다.
3. 발급 상태 확정 후 DB 트랜잭션 밖에서 로컬 SMTP로 전달한다. 상태는 `pending`·`smtp_accepted`·`failed_or_unknown`이며 SMTP 수락을 수신함 전달 완료로 해석하지 않는다. 자동 재발송과 실패 전용 재요청 UI 없이 기존 메일 요청 화면을 사용한다.
4. 인증 URL의 토큰은 fragment로 전달하고 확인 화면이 메모리에 읽은 뒤 주소에서 제거한다. GET·미리보기는 소비하지 않는다. 대상 이메일 조회와 사용자의 명시 확인을 구분한다.
5. 확인 요청은 링크 목적·미사용·무효화·만료를 다시 검증한다. 사용자 생성/조회·토큰 소비·로그인 세션 생성은 같은 지속 DB 트랜잭션에서 확정한다. 유효한 다른 계정이 로그인돼 있으면 자동 교체하지 않는다.
6. 탈퇴 재확인은 원래 요청한 로그인 세션과 대상 이메일을 확인하고 그 세션 행에 최종 탈퇴 권한을 기록한다. 탈퇴 확정은 권한 소비·계정 차단·전체 세션 무효화·삭제 작업 등록을 같은 지속 트랜잭션에서 수행한다. 이후 지연 저장도 계정 상태를 확인해야 한다.

## 시각·동시성·접근 제어

서버/DB UTC 절대 시각으로 `현재 시각 >= 만료 시각`이면 만료다. 잠금 대기 뒤에는 DB `clock_timestamp()`로 다시 확인하고 트랜잭션 시작 시각을 현재로 재사용하지 않는다. 인증된 처리는 계정→로그인 세션, 학습 처리는 이어서 학습 세션을 잠그며 활성 계정·유효 세션을 다시 확인한다. 만료·로그아웃·탈퇴 상태를 단순 upsert로 되살리지 않는다.

기록 조회·변경은 서버의 인증과 대상 소유자 검증을 함께 수행하며 요청 사용자 ID만으로 허용하지 않는다. 변경 요청의 출처 검사·개인 응답의 캐시 헤더는 [API 공통 규칙](API.md#공통-요청응답), 토큰과 링크 확인 오류는 [API 오류 계약](API.md#주요-오류와-미정-범위)을 따른다.

인증 상태는 사용자·노트와 같은 지속 DB에 둔다. 별도 인증 DB·Redis·캐시는 추가하지 않는다. 인증 조회량·지연·DB 자원 경합·운영 부담이 관측되면 분리를 재논의한다. 음성 조각마다 DB 조회하는 구조는 요구하지 않으며 장기 직접 연결의 무효화 반영은 미해결이다.

## 정리·복원과 남은 검증

일반 앱/DB 재시작은 유효 인증을 유지하고, 과거 백업 복원 시험에서는 전체 인증을 무효화한다. 효력 종료 행과 통합 탈퇴 권한의 독립 정리는 [로컬 기한 작업](LOCAL-OPERATIONS.md#기한-작업), 복원 제약은 [백업](LOCAL-OPERATIONS.md#백업과-복원-경계)을 따른다. 유효 로그인까지 삭제하거나 만료 상태를 갱신으로 되살리지 않아야 한다.

합성 동시성·브라우저 검증과 한계는 [2026-10-23](../worklogs/2026-10-23.md), [2026-10-25](../worklogs/2026-10-25.md), [2026-10-27](../worklogs/2026-10-27.md)을 따른다. 실제 메일 서비스·전달/반송·운영 권한과 인증 검증, 확인 성공 뒤 응답/쿠키 유실의 복구 상세, 장기 연결 차단은 남는다. 운영 검증 완료를 뜻하지 않는다.

## Google 로그인: 승인된 미구현 범위

이메일 링크와 Google OAuth/OIDC를 함께 제공하고 제공자 인증 이후 앱 계정·학습 기록·세션은 공통으로 관리한다([DEC-057](../adr/057-GOOGLE-LOGIN-ALONGSIDE-EMAIL.md)). 최초 로그인·세션 만료 후·과거 백업 복원 후 재로그인에 이메일 링크와 Google을 모두 지원하는 것이 승인된 제품 계약이다. 현재 로컬 구현은 합성 이메일 링크만 지원하며 Google 로그인 구현·매핑 스키마·라이브러리 선택은 없다. 계정 연결·중복 가입·연결 해제, Google 전용 가입자의 이메일 확보·탈퇴 재확인과 콜백 보안 상세는 D-02에서 합의한다. 이메일 일치 자동 병합은 채택하지 않았다. Gemini 음성 API 키·단기 토큰과 소셜 로그인 자격은 별개다.
