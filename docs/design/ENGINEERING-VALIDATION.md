# 엔지니어링 검증 설계

작성일: 2026-10-20. 상태: 검증 지침, 실제 실험 결과는 날짜별 worklog에 기록. 관련: PRD O-01/O-03/O-06/O-08, V-05, C-04~C-06.

요구사항은 [PRD](../PRD.md), 구조·기술적 가정은 [DESIGN.md](../DESIGN.md)를 기준으로 한다. 이 문서는 측정·실험 방법만 정의하며 특정 관측 도구·클라우드·배포 구조를 채택하지 않는다.

## 단계별 검증과 판정

가짜 데이터·가짜 AI 응답의 로컬 흐름부터 확인하고 실제 AI·음성을 순차 연결한다(DEC-006/007). 제품 규칙은 자동 테스트로, 생성형 AI 품질은 고정 시나리오와 평가 기준으로 구분한다. 개발 순서·의존성과 작업 완료 판정은 [TASKS](../TASKS.md#선행-관계)를 따른다.

기준선 전에 기능·부하·데이터 규모·실행 환경·측정 구간을 정하고, 수치 목표는 사용자 경험·예산 근거와 함께 초기 목표로 제안한다. 실험 수행·원인 확인·개선 적용·효과 검증을 구분하며 결과가 없으면 계획/가정으로 표시한다. 테스트 환경의 장애 실험과 실제 운영 장애는 별도로 기록한다.

## 최소 관측

| 대상 | 사용자 관점의 측정 | 같은 요청·시간 구간에서 연결할 관측 |
| --- | --- | --- |
| 대화 응답 | 텍스트 제출→화면 응답, 음성 발화 종료→첫 응답 음성 재생의 지연·실패 | 앱 처리·외부 AI 응답 대기, CPU·메모리·처리 대기 |
| 끼어들기 | 감지→실제 재생 중단 지연, 생성 취소 실패 | 취소 요청·응답 시점, 연결 상태·늦은 이벤트 |
| 종료·노트 | 종료 요청→노트 표시 지연·실패 | 요약 API 대기, 저장·조회 시간·연결 풀 대기 |

각 기능이 구현되는 단계에 해당 지표만 추가한다. CPU·메모리는 초기 자원 관측으로, 이벤트 루프·워커·연결 풀 대기는 선택한 구조와 증상에 맞춰 추가한다. 모든 자원을 수집하는 것보다 주요 요청의 성능과 실패를 설명할 수 있는지 먼저 확인한다.

요청·세션 식별자와 시간 구간으로 사용자 증상과 시스템 관측을 연결한다. 식별자는 고카디널리티 지표 라벨로 무조건 추가하지 않고 요청 추적에 사용한다. 브라우저가 공급자에 직접 연결되는 구간은 브라우저 측 시점도 확인한다. 서로 다른 장치의 시각을 단순 차감하지 않고 각 구간의 로컬 경과 시간·상관 정보를 사용하며 시각 오차와 미관측 구간을 남긴다.

실제 연결 후 10분 세션과 사용자별 월 비용을 실측하거나 사용량·단가·실패/재시도 등 조건을 명시해 추정한다. 공급자가 내부 시간을 제공하지 않으면 외부 호출 전체 대기로 기록한다. 음성 인식·모델·합성 시간을 임의 분해하지 않는다. 원문 발화·음성·비밀값은 관측 로그에서 제외한다. 추적 식별자의 접근·보관 범위도 데이터 정책에 맞춘다.

## 정상 기준선과 비교

1. 기능·버전·환경·자원 설정·공급자·모델을 기록한다.
2. 정상 흐름에서 동시 세션 수·요청 빈도·대화 길이·저장 데이터 규모를 명시해 기준선을 수집한다.
3. 지연 분포와 오류 건수/전체 시도 수, 준비 구간·측정 구간·표본 수를 구분한다. 실패·시간 초과를 성공 지연 표본에서 제외했다면 별도 집계해 숨기지 않는다. 표본이 부족한 백분위는 대표 성능으로 단정하지 않는다.
4. 기준선 확보 후 부하를 단계적으로 높이며 사용자 지연과 자원·대기 변화를 함께 확인한다.
5. 개선 전후에는 동일 시나리오·부하·데이터·환경·측정 구간을 적용한다. 외부 서비스·네트워크 변동과 불가피한 차이는 비교 한계로 기록한다.

부하·표본 수·측정 시간은 목적과 허용 예산을 근거로 실험 전에 정한다. 현재 임의 수치는 지정하지 않는다. 가짜 공급자 결과는 앱 내부 흐름의 기준선이며 실제 AI·음성 성능과 구분한다. B-00에서 실제 공급자 비용·성능을 검증했다고 보고하지 않는다.

## 부하·실패 실험

운영과 분리된 테스트 환경에서 합성 데이터·테스트 계정을 사용한다. 환경 분리의 구체적인 방식은 D-05에서 결정한다. 비용·데이터 범위를 합의하기 전 유료 호출이나 실제 사용자 기록을 실험에 사용하지 않는다.

- 부하 증가: 동일 사용자 시나리오에서 동시 세션·요청 빈도·데이터 규모를 통제해 단계적으로 변경한다. 한 실험의 변경 변수를 명시한다.
- 의존 서비스 실패: AI 응답 지연·시간 초과·요청 거절·연결 단절, 저장소 실패를 테스트 대역이나 통제된 실패 주입으로 재현한다. 실제 외부 서비스에 장애를 유발하지 않는다.
- 배포·데이터 복구: 기존 C-03/C-05의 잘못된 배포·백업 복원 검증을 유지한다.

실험 전에 영향 범위, 비용·자원 중단 기준, 정리·복구 방법을 정한다. 사용자 증상·자원·대기의 상관관계만으로 원인을 확정하지 않고 추가 실험으로 원인 후보를 좁힌다. 개선 시 사용자 경험·데이터 정합성·오류·비용의 악화도 확인한다.

병목이 확인되지 않으면 결과를 꾸미지 않고 미완료 사유와 다음 실험을 남긴다. 개선 효과가 없으면 효과 없음으로 보고한다. 실험 수행·원인 확인·개선 적용·효과 검증을 구분한다.

## 실제 실험 시 기록 위치와 형식

인증 메일 30초 발급 간격의 저장 방식은 별도 시험 DB에서 합성 이메일 수·이메일당 요청 수·동시 연결 수를 통제해 비교한다. 별도 제한 행 조회와 요청 테이블의 최신 발급 시각 인덱스 조회를 비교하며, 조회만의 지연과 잠금·쓰기 포함 발급 처리·동일 이메일 경쟁·인덱스 공간을 분리해 기록한다. 공통 사용자 확인·HTTP·메일 전송을 제외했다면 전체 앱 성능으로 해석하지 않는다. [재현 스크립트](../../app/scripts/benchmark-auth-rate-limits.mjs)와 [2026-10-26 실험](../worklogs/2026-10-26.md)을 따른다. 이 비교는 스키마 변경의 채택이 아니다.

실제 실험일의 `docs/worklogs/YYYY-MM-DD.md`에 아래 절을 작성한다. 결과 파일·성공 사례를 미리 만들지 않는다. 큰 원시 증거는 비밀값·사용자 데이터가 없는지 검토한 뒤 별도 경로로 보관하고 worklog에서 연결한다. 같은 결과를 설계·PRD·ADR에 복사하지 않으며 결정에 필요한 근거만 링크한다.

```md
### EXP-YYYYMMDD-NN · 실험명

- 구분: 테스트 환경 실험 | 실제 운영 장애
- 연결 요구사항·작업:
- 증상·가설과 판단 기준:
- 실험 조건:
  - 버전·환경·자원·공급자/모델:
  - 대상 기능·부하·데이터 규모:
  - 측정 지표·준비/측정 구간·표본 수:
  - 실패 주입·중단 기준·정리/복구 방법:
- 관측 결과와 증거:
- 원인과 근거:
  - 확인한 원인 / 남은 가설 / 미확인 구간
- 개선 내용:
- 동일 조건 재검증:
  - 개선 전후 결과·반복 횟수·차이·비교 한계
- 복구 시간·데이터 손실 범위: 해당 시
- 재발 방지·후속 작업:
- 판정: 효과 확인 | 효과 없음 | 판단 보류
```
