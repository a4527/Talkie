# ADR-034 · DEC-034 · 별도 PostgreSQL에 임시 원문 저장·삭제

- 결정일: 2026-10-23
- 상태: Accepted
- 동의 근거: 사용자가 지속 DB 1A를 재확인한 뒤 임시 원문에 Redis와 DB 중 어느 쪽이 나은지 질문했다. Redis 휘발성/영속화와 백업 경계를 분리한 PostgreSQL 저장·삭제를 비교하고 후자를 추천한 설명에 “그렇게 하자”라고 동의했다. 앞선 2A는 별도 인스턴스/볼륨 안이며 이를 임시 저장 구성으로 채택한다.
- 배경: 임시 원문은 삭제 전까지 중단 재개·노트 재시도의 유일한 근거다. DEC-027의 복원용 백업 제외와 DEC-012/024의 보관 기한을 동시에 만족해야 한다. DEC-033의 지속 DB 엔진 선택만으로는 임시 저장을 결정하지 않았다.

## 대안과 선택 이유

| 대안 | 장점 | 부담·한계 |
| --- | --- | --- |
| 별도 PostgreSQL 인스턴스·볼륨 · 채택 | 같은 DB 기술을 재사용하고 일반 재시작 후 저장 원문 복구를 검증할 수 있다. 지속 기록과 백업 경계를 분리한다. | DB 두 벌의 실행/권한/볼륨과 삭제 작업·저장소 간 실패 처리가 추가된다. 백업 없는 디스크 손실은 복구하지 못한다. |
| 영속화 없는 Redis | TTL을 통한 만료와 디스크 영속 파일 없는 구성이 가능하다. | Redis 재시작 시 이미 저장한 원문도 유실돼 재개/노트가 실패할 수 있다. 별도 기술·메모리 용량·축출/쓰기 실패 관리가 필요하다. |
| 영속화 Redis | TTL과 디스크 기반 재시작 복구를 함께 사용할 수 있다. | AOF/RDB·동기화 정책별 유실·재작성·잔존/백업 관리가 추가된다. 삭제 예정이라는 이유만으로 DB보다 간단해지는 것은 아니다. |
| 별도 SQLite 파일 | 파일 기반 실행으로 구성할 수 있다. | PostgreSQL 외 두 번째 엔진·파일/저널/백업 제외와 동시성 관리가 필요하다. |
| 지속 DB와 같은 인스턴스의 별도 테이블/스키마 | 실행 구성과 일부 트랜잭션 처리가 단순하다. | 전체 물리 백업/WAL 아카이브에 원문이 섞일 수 있다. 단순 테이블 분리를 백업 제외로 보장하지 않는다. |

원문을 재생성 가능한 캐시로 보지 않고, 보관 기한 동안의 내구성과 이미 선택한 엔진 재사용을 우선한다. TTL 편의나 미측정 성능을 근거로 Redis를 추가하지 않는다. Redis가 일반적으로 부적합하다는 결정은 아니며 현재 Talkie의 정책·규모 미측정 상태에 대한 판단이다.

## 결정과 데이터 경계

- 임시 전체 대화 글을 지속 기록 DB와 별도 PostgreSQL 인스턴스·볼륨에 저장한다. 같은 호스트에서 실행할 수 있으며 별도 VM·관리형 상품·클라우드·유료 자원은 채택하지 않는다.
- 임시 원문 볼륨을 앱 복원용 백업·스냅샷과 외부 WAL 아카이브 대상에서 제외한다. 호스트 전체 스냅샷이 두 볼륨을 함께 담지 않는지도 검증한다. 제공 환경이 이를 충족하지 못하면 연결 전에 재논의한다.
- 일반 재시작 복구용 로컬 데이터/WAL은 존재한다. SQL DELETE가 디스크 흔적을 즉시 덮어쓰거나 모든 사본을 지우는 보장은 아니다. 현재 접근 가능한 데이터 삭제와 백업 제외, 로컬 물리 잔존을 구분해 검증하며 매체 완전 소거를 약속하지 않는다.
- 명시/자동 종료 후 노트·근거 검증 및 저장 완료(부분 노트 포함) 시 즉시 원문 삭제, 실패해도 최초 종료 후 최대 24시간을 유지한다. 중단 후 재개 24시간은 별도다. 저장·재시도로 최초 삭제 기한을 연장하지 않는다.
- 작업 대상·최초 기한은 DEC-028의 지속 작업 목록으로 관리한다. 두 저장소의 업데이트가 하나의 원자 트랜잭션이라는 가정을 하지 않고 재시도·중복/늦은 저장·기한 만료/탈퇴 후 재생성 방지 계약을 구현한다. 만료 데이터 접근도 차단한다.
- 원본 음성 미저장과 사용자별 접근 통제, 기존 지속 기록 백업/보관 정책은 유지한다. 인증 상태 저장 방식(첫 묶음 3번)은 아직 미정이다. B-00 메모리 범위는 확대하지 않는다.

## 영향·근거·미검증

- 비용/일정/운영: 두 DB 프로세스·볼륨의 설정·접근 권한·상태 관측·기한 작업·복원 시험이 추가된다. 같은 엔진을 써도 두 저장소 간 장애 처리는 필요하다. 실제 자원/가격/지연/성능은 미측정이다.
- 사용자/데이터: 일반 재시작의 재개 가능성을 높이는 방향이지만 구현 검증 전이다. 임시 저장 디스크 손실 시 원문을 백업에서 복원하지 못해 노트가 누락될 수 있으며 이를 안내한다. 보관 기한을 늘리지 않는다.
- 관찰한 공식 자료(2026-10-23): [Redis 영속성](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [Redis EXPIRE](https://redis.io/docs/latest/commands/expire/), [Redis 메모리 관리](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/), [PostgreSQL vacuum](https://www.postgresql.org/docs/current/routine-vacuuming.html), [PostgreSQL 백업/WAL](https://www.postgresql.org/docs/current/continuous-archiving.html).기능 설명과 달리 Talkie 적합성은 위 요구에 근거한 설계 판단이다.
- 미확정: 실행 버전/도구·로컬 구성·스키마·두 저장소 계약·삭제 실행 주기/장기 실패 대응·호스팅/백업 제공 방식. 설치·복원·물리 잔존 분석·성능 실험은 아직 없다.
- 검증 위험: 별도 저장소의 부분 커밋·볼륨 손실과 백업 경계 누락 때문에 재개 근거 손실 또는 삭제 원문 부활이 생길 수 있다. 두 DB 실패·원문 삭제/늦은 저장의 경쟁과 복원용 사본 제외가 이 선택의 핵심 검증 대상이다. 기능별 사례·완료 판정은 [TASKS의 B-05/B-06](../TASKS.md#첫-학습-흐름과-기능-구현), 저장·삭제 계약은 [학습 저장 설계](../design/LEARNING-PERSISTENCE.md), 백업 검증 경계는 [로컬 운영 설계](../design/LOCAL-OPERATIONS.md#백업과-복원-경계)를 따른다.
- 재검토: 백업 제외 불가능·기한 준수 실패·두 인스턴스 운영 부담·관측된 처리량/비용 문제가 생기면 Redis/SQLite/다른 분리 구성을 다시 비교한다.
- 대체 관계: DEC-027의 미정 임시 저장 방식 구체화. DEC-012/013/024/028/033을 대체하지 않는다.
- 연결: DESIGN.md, D-02/B-05, 최소 MVP 점검표 L07. D-02 완료를 뜻하지 않는다.
