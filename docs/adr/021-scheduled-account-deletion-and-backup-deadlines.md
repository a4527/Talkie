# ADR-021 · DEC-021 · 탈퇴 데이터 일괄 삭제와 백업 7일 기한

- 결정일: 2026-10-21
- 상태: Accepted
- 동의 근거: 탈퇴 즉시 접근 차단·서비스 데이터 24시간 이내 삭제·백업 30일 이내 삭제안을 제시하자 사용자가 “탈퇴즉시 차단하고, 24시간 이내 데이터 삭제하는데 삭제 시간을 정해서 한번에 처리하도록 하는건 어때? 백업은 1주일 주자”라고 명시했다. 일괄 처리 방식을 채택하고 백업 제안은 7일로 수정했다.
- 배경·확정 제약: DEC-019의 계정·연결 학습 데이터 전체 삭제와 DEC-020의 탈퇴 전 이메일 재확인·전체 로그인 세션 무효화를 따른다. 이번 결정은 미정인 삭제 일정과 백업 기한을 구체화한다.
- 대안: 탈퇴 요청 안에서 즉시 전체 삭제하면 대기 기간이 짧지만 연결 데이터 삭제의 지연·실패가 요청 처리에 영향을 준다. 탈퇴별 비동기 작업은 일찍 삭제할 수 있지만 개별 작업 실행·재시도 관리가 필요하다. 정해진 시각의 일괄 삭제는 대상을 모아 처리할 수 있지만 작업 지연·실패가 여러 탈퇴 건의 기한에 영향을 줄 수 있고, 처리 시간과 재시도 여유가 필요하다. 백업 30일안은 복원 자료를 오래 유지하지만 탈퇴 데이터도 오래 남는다. 7일안은 보관 잔여 기간을 줄이는 대신 장기 백업 보존과 복원 가능 시점에 제약을 준다.
- 결정: 탈퇴 확정 즉시 접근 차단·전체 로그인 세션 무효화, 앱 관리 계정·연결 학습 데이터는 정해진 시각의 일괄 작업으로 탈퇴 후 24시간 이내 삭제, 앱 관리 백업의 해당 데이터는 탈퇴 후 7일 이내 제거 또는 포함 백업 만료·폐기로 확정한다. 현재 동작은 [PRD 8.2절](../../PRD.md#82-탈퇴-데이터-일괄-삭제와-백업-기한)을 따른다.
- 이유: 사용자는 접근 차단과 데이터 삭제를 분리하고 삭제를 모아서 처리하길 원하며 백업에도 1주일의 정리 기한을 지정했다.
- 영향·비용·일정·사용자 경험·데이터·운영: 탈퇴 응답은 일괄 삭제 완료를 기다리지 않지만 삭제 대기 중 데이터 접근과 늦게 도착한 작업의 저장을 막아야 한다. 삭제 대상·최초 기한·완료 여부를 추적하고 중복 실행·실패를 처리하는 기능과 검증이 필요하다. 일괄 삭제의 비용 절감은 아직 측정하지 않았다. 백업 정책·폐기·복원 절차가 7일 기한을 지원해야 하므로 공급자·저장 기술 선정에 제약이 생긴다. 백업을 단순히 생성 후 7일 보관하면 탈퇴 후 삭제 대기 중 새로 만들어진 백업이 탈퇴 후 7일을 넘을 수 있으므로 별도 확인해야 한다.
- 검증 범위: 일괄 작업 직전·직후 탈퇴와 처리 지연·작업 실패·중복 실행에서도 최초 탈퇴 후 24시간 기한과 접근 차단을 확인한다. 진행 중 AI/노트 작업의 늦은 저장과 로그인 세션 재사용을 막는지 확인한다. 탈퇴 후 삭제 대기 중 생성된 백업까지 포함하여 최초 탈퇴 후 7일 기한을 검증하고, 복원 뒤 서비스 공개 전에 탈퇴·삭제 상태가 재적용되어 데이터가 되살아나지 않는지 확인한다.
- 한계·남은 상세: 정책 합의이며 구현·삭제·백업 복원 실험은 수행하지 않았다. 구체 삭제 실행 시각·실행 기술·재시도 간격/횟수·실패 알림·복원 시 삭제 상태 재적용에 필요한 최소 정보의 보관·공급자 처리 조건은 삭제 기능 구현 또는 해당 연결 전에 확정한다. 장시간 장애 시에도 자동으로 기한이 연장되는 정책은 아니다. 체험 기록 만료·임시 원문 삭제의 백업 처리 기한을 이번 탈퇴 정책에서 자동 도출하지 않는다.
- 재검토 조건: 저장·백업 공급자의 제약이나 실패 실험에서 기한 준수가 불가능하면 실제 데이터 연결 전에 대안과 영향을 제시해 재논의한다.
- 대체 관계: DEC-019·DEC-020의 미정 탈퇴 삭제 일정·백업 처리를 구체화한다. 기존 결정의 기능 범위와 로그인·기록 보관 정책은 유지한다.

## 후속 상태 연결 (2026-10-21)

기한 작업의 실행 방향은 후속 [ADR-028](028-durable-scheduled-work-list.md)의 지속 목록·정시 실행을 따른다. 임시 전체 원문은 [DEC-027](../../DECISIONS.md#dec-027)에 따라 앱 복원용 백업에서 제외하며, 체험 만료 기록의 백업 처리는 여전히 미정이다. 실제 플랫폼과 실패/복원 처리의 검증은 남아 있다.
