# ADR-033 · DEC-033 · 지속 기록 DB로 PostgreSQL 채택

- 결정일: 2026-10-23
- 상태: Accepted
- 동의 근거: 사용자가 SQLite와의 비교 및 MySQL·MariaDB 대비 장점/한계를 확인한 뒤 “선택 이유까지 잘 정리해서 postgres 선택하자”라고 명시했다.

## 배경과 선택 범위

실제 계정별 기록·기기 간 재개·지속 작업 목록을 연결할 DB 엔진이 미정이었다. DEC-032의 계정당 진행 대화 하나, DEC-013/031의 저장 재전송·순서 정합성, DEC-024의 재개/자동 종료 경쟁, DEC-021의 탈퇴 이후 저장 차단을 구현해야 한다.

로컬 실제 기능 단계부터 사용자·지속 학습 기록·노트/근거·작업 목록을 저장할 DB 엔진으로 PostgreSQL을 채택한다. 특정 관리형 서비스·클라우드·리전·요금·버전·ORM·드라이버·배포 구성을 선택하는 결정은 아니다. 임시 원문용 별도 PostgreSQL 인스턴스와 인증 상태를 같은 DB에 저장하는 첫 제안의 2A/3A는 아직 채택하지 않았다. B-00의 가짜 AI·실행 중 메모리 범위도 유지한다.

## 비교한 대안과 선택 이유

| 대안 | 이점 | 부담과 이번 판단 |
| --- | --- | --- |
| PostgreSQL · 채택 | 조건부 고유 인덱스로 특정 상태에서만 유일해야 하는 규칙을 직접 표현할 수 있다. JSONB와 관련 인덱싱, 행 단위 접근 정책을 제공한다. 서버 DB 기반 동시 처리·복원 검증을 로컬부터 이어갈 수 있다. | DB 프로세스·접속·권한·백업·업데이트 관리가 필요하다. 기능 활용에는 스키마/권한 설계와 시험이 따른다. Talkie의 조건부 제약과 향후 서비스 구성에 맞는다는 설계 판단으로 채택한다. |
| MySQL / MariaDB | 트랜잭션·고유 제약·동시 처리로 요구사항 구현이 가능하다. 해당 기술 경험이 있다면 익숙한 운영 도구가 이점일 수 있다. | PostgreSQL의 조건부 고유 인덱스와 같은 규칙은 선택한 엔진/버전에 맞는 대체 설계가 필요하다. Talkie를 구현할 수 없어서 제외한 것이 아니며 성능·비용 열위는 확인하지 않았다. |
| SQLite | 별도 DB 서버 없이 파일 기반으로 시작할 수 있어 로컬 구성과 초기 운영이 간단하다. 현재 기능을 구현할 수 있다. | 쓰기 동시성·파일 접근 경계를 고려해야 한다. 여러 앱 서버 구성으로 바뀌면 서버 DB 이전·마이그레이션·동시성 재검증이 필요할 수 있다. 로컬 시작의 단순함보다 공개 가입·기기 간 재개·지속 작업까지 같은 서버 DB로 검증하는 편을 선택했다. |

가장 직접적인 근거는 계정당 진행 대화 하나를 DB 제약으로 표현하기 쉽다는 점이다. 예를 들어 종료 시각이 없는 행에만 사용자 ID 고유 인덱스를 적용할 수 있다. 실제 열·상태 모델은 아직 미확정이며 연결 소유권·늦은 이벤트·재개 경쟁까지 인덱스 하나로 해결되는 것은 아니다.

JSONB는 형태가 일부 달라질 수 있는 AI 결과/진행 정보에 선택적으로 활용할 수 있다. 사용자·턴·근거 연결 등 명확한 관계를 전부 JSON으로 저장하는 결정은 아니다. MySQL도 JSON을 제공하므로 JSON 지원 자체를 독점적인 선택 근거로 삼지 않는다. 행 단위 접근 정책은 추가 방어 수단으로 검토할 수 있지만 도입을 확정하지 않으며 DB 소유자/특권 역할과 요청 사용자 전달을 올바르게 설계해야 한다.

## 관찰한 사실과 추정·미확인

공식 자료 확인일: 2026-10-23.

- [PostgreSQL 부분 인덱스](https://www.postgresql.org/docs/current/indexes-partial.html): 조건에 맞는 행에만 인덱스·고유성 적용 가능.
- [PostgreSQL JSON](https://www.postgresql.org/docs/current/datatype-json.html), [MySQL JSON](https://dev.mysql.com/doc/refman/8.4/en/json.html): 양쪽 모두 JSON 처리 기능을 제공하며 구현/인덱싱 방식에 차이가 있다.
- [PostgreSQL 행 보안](https://www.postgresql.org/docs/current/ddl-rowsecurity.html): 행별 조회·변경 정책을 제공하지만 소유자 등 우회 경계가 있다.
- [MySQL 잠금 조회](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html), [MariaDB SELECT](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/select): SKIP LOCKED 같은 작업 분배 수단은 PostgreSQL만의 이점이 아니다.
- [SQLite 사용 범위](https://www.sqlite.org/whentouse.html): 단순 파일 기반 구성과 쓰기 동시성·다중 서버 접근의 고려사항을 설명한다.
- [PostgreSQL 물리 백업·WAL 복원](https://www.postgresql.org/docs/current/continuous-archiving.html): 엔진 채택만으로 임시 원문 백업 제외나 탈퇴 백업 7일 기한을 충족하지 않는다. 같은 인스턴스에서 스키마만 나누는 것을 물리 백업 분리로 취급하지 않는다.

위는 문서로 확인한 기능이다. Talkie에서 구현이 간결해질 것이라는 평가는 추정이다. 현재 부하에 PostgreSQL이 필수이거나 다른 DB보다 빠르고 저렴하다는 근거는 없다. 설치·실측·삭제/복원 시험은 수행하지 않았다. 사용자에게 특정 DB 경험이나 학습 동기가 있다고 추정하지 않는다.

## 영향·검증·재검토

- 비용·일정: 로컬 DB 실행과 마이그레이션·연결·권한·백업 관리, 동시 요청 시험이 추가된다. 관리형 운영비·메모리/디스크 비용은 호스팅과 부하 결정 후 산정한다. 자원 생성·유료 지출 승인은 아니다.
- 사용자 경험·데이터: 중복 대화·기록 충돌을 막는 기반이지만 DB 선택만으로 동작을 보장하지 않는다. 보관/삭제·음성 미저장·접근 차단 정책은 그대로다.
- 검증: 설치/빌드·마이그레이션 재현, 동시 시작의 고유성, 저장 재전송/응답 유실의 중복 방지, 재개/종료/탈퇴 경쟁, 연결·쿼리 실패와 복원/삭제를 해당 기능 수용 기준에 따라 확인한다. B-00 결과로 이를 완료 처리하지 않는다.
- 남은 범위: 임시 저장과 인증 상태 저장 방식, 데이터 모델·인덱스·권한·버전·드라이버/ORM·운영/백업 구성·측정 조건.
- 재검토 조건: 측정된 운영비·유지보수 부담·동시 처리/복원 한계가 허용 범위를 벗어나거나 지원되는 배포 환경/기존 기술 자산이 달라지면 대안을 다시 비교한다. 성능 우위나 이전 필요성을 미리 단정하지 않는다.
- 대체 관계: D-02의 미정 지속 DB 엔진 구체화. 기존 채택 결정을 대체하지 않는다.
- 연결: design.md, D-02/B-05, 최소 MVP 점검표 L06. D-02 전체 완료를 뜻하지 않는다.
